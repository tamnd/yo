# Changelog

What each release changed, why, and what it costs you. The versioning rules and what a section has to contain are in [RELEASING.md](RELEASING.md).

While the major is 0, a minor release may break anything, including the on-disk format. The format is frozen at `M6`, not before.

## 0.3.9 — 2026-09-01

Five pull requests, no milestone, so this is a patch. It is two things at once. The first is the rest of what a cache has to do about time and space that 0.3.8 started: keys that expire now come back on their own rather than waiting for somebody to read them, and picking what to evict stopped forgetting everything it learned between one eviction and the next. The second is the beginning of the memory campaign, which is where the gate says the work is.

The `.yo` layout is untouched. A file written by any 0.3.x opens unchanged. Everything that got smaller here got smaller in the arena, not on disk.

The reason memory is the campaign is the gate report from gamingpc. Every failing row fails on memory and none of them fail on speed. The command itself is cheaper on our side on all nine rows where both sides had a PING to subtract, over a range of 1.07x to 92.09x, and then the peak memory column loses: SADD on the memtier profile at 1.41x the leaner rival, SPOP at 1.29x, SRANDMEMBER at 1.24x. So the question this release starts answering is what a set member and a hash field actually cost.

### Added

- **An active expiry cycle, so dead keys come back without being read.** Lazy expiry answers the correctness question on its own, because every read reaps a key past its deadline on the way past and no client ever sees one. What it does not answer is memory. A cache that writes ten million keys with a one hour deadline and never reads them again holds all ten million forever, because nothing goes past them to do the reaping. The sweep follows Redis's rule, which is to sample, drop what is dead, and go round again while more than a quarter of the sample was dead, so a database full of dead keys gets swept hard and a clean one gets one cheap look.
- **A count of the keys that carry a deadline, which `INFO keyspace` was reporting as zero.** That is a number monitoring reads to know how much of a cache is volatile, and a constant is worse than nothing there. It is kept exact and it is free, because both funnels already have the record in hand: every record written goes through one place that now peeks at the old value on the branch that had already loaded its header, and every record removed goes through a sibling of the same shape.
- **An eviction pool, so sampled policies keep their good candidates between rounds.** Before this, picking a victim drew five keys, kept the worst one and forgot the other four, so the key that came second in a five key draw was gone by the next eviction even though it was still there and still a better answer than most of what the next draw would find. The pool holds sixteen, which is what Redis holds and which is about three rounds of sampling at the default of five.

### Changed

- **An element row is eight bytes instead of twelve.** A row held six bytes of name reference and four of home slot, and the alignment of the wide field made it twelve, so the row array of every set, hash and sorted set was carrying a third of itself as padding. The blob offset keeps its whole word because a large collection's names run to megabytes, and the other word now holds the name length in the low byte and the home slot in the twenty four above it. Twenty four bits of home covers every table up to sixteen million slots, which holds twelve million elements, and past there the home is recovered by hashing the name on a cold out of line arm. A name over two hundred and fifty five bytes writes its real length into the two bytes ahead of it in the blob and puts a sentinel in the byte.
- **A hash value's length lives in the blob instead of beside the offset.** The row payload was an offset and a length at four bytes each, and the length did not need to be there, because a value already has somewhere to keep its own length. One byte of prefix under two hundred and fifty five bytes, five above, against four bytes beside every offset. HSTRLEN is the one thing that got worse: it used to read the length out of the row and now takes a byte off the front of the value, which costs the cache miss a caller reading the value would have taken anyway.
- **A volatile eviction policy on a database with no deadlines answers in one comparison.** It used to draw four rounds of buckets and be told there was nothing eligible by every key in all of them, on a path where a client is waiting for the write that eviction is making room for. The count of keys carrying a deadline is what makes that one comparison, and it is the first step towards the second dictionary the `ROUNDS` doc has been naming for a while.
- **`allkeys-random` and `volatile-random` skip the pool entirely.** They pick by a fair draw and have no ordering for a pool to approximate, so under those two every eligible key already is the answer and sixteen slots would be pure overhead. Changing the policy throws the candidates away, because a score under one policy means nothing under another, and so does a flush.

### Performance

Development measurements on the arm dev machine unless the machine is named. None of these are gate numbers.

- **An element row array is a third smaller, which on sixteen byte members is between four and five bytes off every member.** A thousand members went from 36.96 bytes a member to 32.83, a hundred thousand from 43.53 to 38.72, and a million from 42.11 to 37.23. The last of those is 4.9 bytes a member, which is 11.6 percent of what the set costs and 18.7 percent of what it costs on top of the bytes the caller actually stored.
- **A hash field is three bytes cheaper by arithmetic and 2.18 by peak RSS.** On server3, five hundred thousand fields of `field-%08d` and `value-%08d`, peak resident set went from 27,576 KiB to 26,512 KiB. The gap between the two numbers is the value blob's own growth rounding. The in process reading is not the one to trust for this because it reports capacity rather than live bytes, and it moved in both directions at different sizes since one extra byte per value crossed a growth threshold.
- **A warm eviction pool allocates nothing.** Its sixteen slots own their key buffers and reuse them, and the array itself is not allocated until the first candidate is offered, so a database that never evicts pays nothing at all for it. There is a test asserting each of those.
- **The removal path is the one to watch on the row packing.** Backshift deletion reads the home slot once per slot of the run behind the hole. Left as a single function with the hash call in the cold arm, that call stopped the whole thing inlining into the loop and a pop of a thousand members measured 52 percent slower. Split with the cold arm out of line, a pop is level at a thousand and faster at a hundred thousand and a million, because the row array the backshift walks is a third smaller.

### Known

- **A hash field is eighteen bytes of overhead and the memory row wants sixteen.** Eight of row, four of offset, one of value length, and about five of slot array, on an eight byte name and an eight byte value. Eighteen is the floor for this layout, because the only way past the row is to stop interning field names, which puts the name back in front of every value and pays for it again on every rewrite. The remaining five is the slot array.
- **The slot array cannot be shrunk on its own.** Slots per member is one over the load factor and an unsuccessful linear probe costs about half of one plus one over the square of one minus the load, so the memory an open addressed array costs and the length of a probe through it are the same dial seen twice. Sizing the array to the table exactly and growing it by a quarter rather than doubling was tried and measured on gamingpc: a quarter of the memory back for probe_miss up fifty to ninety percent, fill up fifty six and pop up a hundred and forty five. That is not affordable against a SADD row that is 1.09x at memtier P16. The change that takes the memory without paying throughput is probing the array in groups with SIMD off the tag byte the row packing already put in the top of every slot, which is `#178` and is not in this release.
- **The active expiry ratio is measured over a different denominator than Redis's.** Redis samples out of its expires dictionary, so every key it looks at could be dead. There is no second dictionary here yet, so the sample comes off the main index and most of what it looks at may carry no deadline at all. A quarter of every key sampled is a bar a database that is one percent volatile could never clear however much dead memory is sitting in it, so the ratio is over the keys sampled that could have expired.
- **`avg_ttl` is still a zero.** Redis reports a zero there too on a server that has never run its active expiry cycle, because that number is a running estimate the cycle produces rather than something anybody measures on demand.

## 0.3.8 — 2026-09-01

Nine pull requests, no milestone, so this is a patch. Almost all of it is the first half of `M5`: eviction, which is the thing a cache does that a store does not, and which this server did not do at all until now. Before this release `maxmemory` was a setting you could write and nothing would read, and a server that filled up stayed full. After it, a server with a limit and a policy makes room the way Redis makes room, and one with no policy refuses the write with the same line Redis refuses it with.

The `.yo` layout is untouched. A file written by any 0.3.x opens unchanged. The record that grew by three bytes is the one in the arena, not the one on disk, and the format crates were not touched at all this release.

### Added

- **The LRU clock and the LFU counter, and all ten policies.** There are ten `maxmemory-policy` values in Redis 8.8, not eight: `volatile-lrm` and `allkeys-lrm` are least recently modified and are easy to miss because nearly everything written about Redis eviction predates them. Both readings share the same twenty four bits, because a key is only under one policy at a time. Under LRU the field is a clock in seconds that wraps every hundred and ninety four days, and under LFU it is sixteen bits of minutes over an eight bit logarithmic counter that Redis probabilistically increments and halves as the key goes cold.
- **Three bytes in every record for that field**, after the deadline and before the payload. In the record and not in the index, because an index bucket is exactly one cache line and fully packed with seven tags, a flags byte, seven addresses and a link, and there is no room in it for a per entry field without giving up the single probe the whole index rests on. Redis puts its own in the object header for the same reason.
- **Sampling, which is how a victim gets picked.** Redis settled on sampling over ordering in 3.0 and it is the right answer: a server that has run out of room has a client waiting on the write it is making space for, and finding the genuinely least recently used key out of forty million means maintaining an ordering over all of them on every read of every key forever, to make a decision that is a guess about the future either way.
- **`CONFIG SET maxmemory`, with the units.** This is Redis's `memtoull` down to the trap in it: `k` is a thousand and `kb` is a kibibyte, `m` is a million and `mb` is a mebibyte, and the same again for `g`. A value that is not a memory value is refused with the sentence Redis refuses it with and the old limit is left alone. `CONFIG GET` reads it back in plain bytes whatever was typed to set it, and `INFO memory` reports it in the field that used to be hardcoded to zero.
- **A running total of what the collections hold.** Working out how much a database is using meant asking every set, every hash, every list, every sorted set and every array, which is one question per collection, and a server with a limit needs that number once a batch and again on every command that is already over. The slab now keeps the total as the collections move, because the only way to change one is through `get_mut` and so the slab sees every collection that is about to move before it moves. On two hundred thousand small sets the reading goes from 259.8 microseconds to 1.9 on the arm dev machine, and the walk grows with the keyspace while the reading does not.

### Changed

- **A server over its `maxmemory` evicts before it runs the command, and refuses only when there is nothing left to evict.** That distinction is Redis's and it is the one that is easy to get wrong. `performEvictions` answers `EVICT_FAIL` only when it has run out of things to delete, and `processCommand` refuses the client on that and on nothing else, so running out of the time slice part way through a job it is doing well lets the command through. This bounds the loop by a count of sixty four keys rather than by a slice of time, because there is no timer here to hand the rest to, and leaves the rest to the next command. A command that only reads or only frees goes through with nothing left, so a client can dig itself out with `DEL`.
- **Eviction compacts as it goes.** Dropping a key marks its record dead and gives nothing back until a whole segment is empty, so a loop that only evicted would throw the entire keyspace away and watch the memory reading stay where it was. The two arena ratios that decide when a segment is worth collecting also never fire under eviction pressure, because uniform eviction makes every segment equally dead, so there is now a hard mode that ignores both and is only ever reached by a server that is already over its limit. At a limit the copying is cheaper than the alternative, which is telling a client no.
- **Every record write goes through one funnel that stamps the access field.** That is the same moment Redis stamps at, in `createObject`, and it matters more than it looks: a record written and never read would otherwise have an all zero field, an all zero field reads as used right now, and now keeps moving, so a key nobody has touched since it was written would have reported an idle time of zero forever.

### Fixed

- **The two ring tests were bounded by a count of polls rather than by the clock.** A hundred thousand non blocking polls is a few milliseconds of spinning on a quiet machine, and an fsync against network attached storage under a shared CI runner does not always come back inside that, so both tests failed on `main` and passed on a branch minutes earlier with the same code. They now wait thirty seconds and yield between turns. A ring that never completes still fails, it just fails because it never completed rather than because the machine was busy.
- **The hot key memo is measured rather than asserted.** It has been in the keyspace since the `SCAN` work and nothing ever said what it buys. The A/B is a second benchmark row that alternates between two sets, which defeats the memo on every command while leaving both keys, both records and both slabs as warm in cache as the one key was, so the difference between the two rows is the memo and close to nothing else.

### Known

- **The limit is honoured to within one two megabyte segment**, because space comes back a segment at a time. A `maxmemory` of a few hundred megabytes gets what it asked for and a `maxmemory` of four megabytes is asking for a precision this store does not have. This is `D-23` in the divergence register.
- **`Slab::memory_bytes` is now `Slab::slot_bytes`**, because there are three ways to ask a slab what it costs rather than one and the old name did not say which. The old name still works and is deprecated, and it goes at the next minor. Nothing outside the workspace is meant to depend on `yo-kv` directly, but a patch does not take a public item away.
- **The eviction inversion in `M5` is a third done.** `maxmemory` migrating to the file and `maxstore` doing the evicting both need a storage tier that does not exist yet. The `maxstore 0` regime, which is the one that behaves exactly like Redis, is what this release implements.

## 0.3.7 — 2026-09-01

Four pull requests, no milestone, so this is a patch. It is the end of the allocation campaign that 0.3.6 started. The report that came out of that release listed thirteen places where serving a command asked the allocator for memory, and this release takes that list to zero and then makes it a check that runs on every push, so it cannot quietly come back.

The `.yo` layout is untouched. A file written by any 0.3.x opens unchanged.

### Added

- **`cargo xtask alloc`, and it is a CI job.** It builds a debug `yodb` with the allocation check in report mode, sends about nine thousand commands covering every type, and fails if anything on a command path asked for memory. The workload is a Python file in the repository rather than a shell pipeline somebody remembers, so widening it is an edit and not an act of archaeology. Debug on purpose: a release build inlines the interesting frames into each other and every site comes back naming `serve_command`, which tells nobody anything.
- **Three named claims in `yo-alloc`, for the allocations that are not bugs.** `first_touch` is a key coming into existence, `for_the_data` is a collection growing because more was put in it, and `high_water` is a buffer the database keeps reaching a size it has never been asked for before. They are all `allow` underneath and the only difference is what they assert, which is the point: `git grep first_touch` stays a list of the places a key is created, rather than a list of everywhere somebody wanted the check to be quiet.
- **`Keyspace::set_with` and `Keyspace::getdel_with`.** The owning `set` and `getdel` stay for the embedded caller who wants a `Vec` back. The `_with` pair hands the old value to a closure where it still lies in the record, before the write or the delete goes over it, which is what the wire wants because it copies that value into a reply and never looks at it again.

### Changed

- **The union's hash table is kept in the database instead of built per call.** `SUNION`, `SUNIONSTORE`, `SINTER` and `SDIFF` all needed somewhere to check for duplicates and all four built it, filled it and dropped it inside one command. The table now belongs to the database and is cleared rather than freed, so it grows when a union is larger than every union before it and not otherwise. That is 1.48x on a `SUNION` over two text sets on the arm dev machine, which is a development measurement and not a gate number.
- **`yo_alloc::allow` is a relaxed load of a static when no thread has ever been marked**, which is every shipped binary and every benchmark. It had to become nearly free because a claim belongs where the growth is, and the union's growth is per member rather than per call, so the guard sits around the insert inside the walk. A guard around the whole walk would be one call instead of thousands and would also hide whatever the caller's closure does, which is the reply buffer for `SUNION` and the destination set for `SUNIONSTORE`. The report is worth more than that.
- **`COPY` settles the destination before it copies anything.** It used to export the source and then find out whether it was allowed to write, which is the difference between a refused copy of a million member set costing nothing and costing the set. A string is now copied as a record, deadline and all, through the database's scratch buffer, so `COPY` over a string allocates nothing at all.

### Fixed

- **`SET ... GET`, `GETSET`, `GETDEL`, `GETEX`, `INCRBYFLOAT`, `RANDOMKEY`, `RENAME`, the string arm of `COPY` and every command that frees a decoder no longer allocate.** They were the rest of the report. Most were a `to_vec` holding a value across a write that was about to go over it, which the scratch buffer or a `_with` closure removes. `INCRBYFLOAT` was reading its own value out to a `Vec` before parsing it, and an int encoded value has no digits to parse anyway, so that arm converts instead of formatting and then parsing back.
- **`COPY k k` no longer frees the body and then writes a record pointing at it.** The wire never asked, because Redis refuses `COPY k k` with an error and so does the dispatch, but the embedded caller can ask and got the worst of the answers available. It now answers the same pair `RENAME` does: taken without `REPLACE`, fine with it, and the key is left alone either way.
- **The `setops_small` benchmark group had two rows claiming the same identifier**, so criterion panicked on the duplicate and the sixty four member rows had never been measured at all. That also means the nightly benchmark smoke run was failing on it rather than smoking anything.

## 0.3.6 — 2026-09-01

Nineteen pull requests, no milestone, so this is a patch. Two things run through it. The array group finished, which makes it 18 of 18 array commands and the fourth complete type. And a memory campaign that started as one measurement and turned into most of the release: a large integer set now costs a seventh of what it did, `LINSERT` and `LPOS` on a long list are five to fifteen times faster, and the allocator has been armed on the command path for the first time so there is a list of what still calls it.

The `.yo` layout is untouched. A file written by 0.3.4 or 0.3.5 opens unchanged.

The 0.3.5 release did reach crates.io in the end. It was tagged before the publish step became a loop that waits out the rate limit, so it stopped with one crate of eighteen uploaded and had to be recovered by dispatching the workflow from `main` against the tag. All eighteen crates are up at 0.3.5 now, and 0.3.6 is the first release where that path was in the tag from the start.

### Added

- **`ARGREP`, and with it the last of the eighteen array commands.** It searches a range of an array with up to two hundred and fifty textual predicates and answers the indexes that matched, or index and value pairs with `WITHVALUES`. `EXACT` is byte equality, `MATCH` is containment, `GLOB` is the pattern language `KEYS` uses, and `RE` is a POSIX extended regular expression.
- **A POSIX extended regular expression engine in `yo-common`.** Redis gets its from TRE, which it vendors under `deps/tre`, and asks it for very little: extended syntax, no submatches, bytes rather than characters, optionally case insensitive, and a yes or no per element, with a backreference refused before it ever runs. So what had to exist was a boolean matcher over bytes, which is a few hundred lines, rather than a general purpose regex crate and its transitive dependencies linked into the C ABI and every language binding.
- **The partitioned band, with a two level descriptor cache.** A collection past 262,144 elements stops being one element table and becomes P of them, each an ordinary table, with a member's partition taken out of bits 32 and up of its hash. It has to be those bits: a table already indexes its slot array with the low 32 bits of the same hash, so partitioning on the low bits would hand every member of a partition the same home slot and turn the table into a linked list. The set is the first collection wired onto it, and a client cannot tell that it happened, because a fourth word coming back from `OBJECT ENCODING` is a client whose assertions break and a split set answers `hashtable` like the table it was.
- **The scheme B order key allocator for list inserts**, so an insert between two neighbours does not run out of room. That is M4's second scope line and Y19 in the locked decisions.
- **`yo-alloc` is armed in `yodb`.** The module has existed since M0 and nothing called it, so Y7, no allocation on a command path, was enforced by nothing. `YO_ALLOC` is now `off`, `report` or `abort`, and a value that is none of those is an error rather than a quiet `off`, because somebody who typed `YO_ALLOC=abrot` believes the check is running. The guard sits around dispatch in the reactor's pump and covers running the commands and nothing else: framing before it and writing replies after it are both allowed the heap. Under the default mode the whole thing is one relaxed atomic load per batch.
- **`yo_common::Small`, a list that stays on the stack until it does not fit.** Up to `N` elements it is an array in the caller's frame and past that it is an ordinary `Vec`. There is no unsafe in it, because everything it holds is `Copy` and the buffer can be filled with a copy of the first element rather than with `MaybeUninit`.
- **`yo_alloc::first_touch`, which is the one exception to Y7 written down.** A key coming into existence has to build a body somewhere and no arrangement of this code avoids it. There are four calls, in `new_set`, `new_hash`, `new_list` and `new_zset`, so the exception is a grep rather than an argument.
- **Measurement tests for what a set and a hash cost per element**, which M3's memory gate row asks for and which had no number against either half.

### Changed

- **A large integer set stays an intset rather than rehashing into a table.** Redis gives up on the intset at `set-max-intset-entries` and converts, which measured here at 24.60 to 30.92 bytes a member against the intset's 4.00, a twelvefold jump in memory for a set that got one member bigger. What forces it is that Redis has one array, and an insert into the middle of one sorted array memmoves the tail, so a million member set moves half a megabyte per `SADD`. Holding the members in runs fixes the memmove without paying the memory, so the conversion is not needed.
- **Set intersection merges sorted arrays when it can, instead of probing.** An all integer set is an intset and an intset is exactly a sorted array, so whenever every operand is one there is something to walk in lockstep, where a touch is a pointer step and a comparison rather than a hash and a random access into a table. That covers most of what `SINTERSTORE` is actually called with.
- **The list's pivot search reads entry headers instead of decoding elements**, and `LPOS` and `LREM` go through the same scan. The old walk was `iter().position(...)`, which ran the full fourteen way entry decoder and built an `Entry` for every element it was about to throw away.
- **A packed entry is written into the blob rather than built in a `Vec` first.** Every edit to a listpack went through one `splice` that built the new entry in a fresh `Vec`, so every `RPUSH`, `LPUSH`, `HSET`, `SADD` and `ZADD` landing in the packed band paid a malloc and a free for a few dozen bytes that never outlived the call, on top of the memmove it was going to do anyway.
- **The release workflow waits out crates.io's rate limit instead of failing on it.** A brand new crate name is limited roughly one every ten minutes against one a minute for a new version of an existing name, and the first release of this workspace was eighteen new names at once. Each pass now asks the registry what is still missing, publishes what it can, and on a refusal sleeps until the time crates.io named. Progress is measured against the registry rather than against what cargo thinks it did, so a pass that uploads three and is then turned away is three crates of progress. Anything that is not a 429 still stops the job.
- **`cargo xtask reserve` asks a registry who holds a name rather than whether the name exists.** The audit was reporting `cocoapods:Yodb` as regressed from `free` to `blocked` on a pod whose owner list has exactly one entry and it is ours.

### Fixed

- **`APPEND`, `SETRANGE`, `EXPIRE` on a string, `ZADD`, `ZINCRBY`, `HINCRBYFLOAT`, `LREM` and `ZRANDMEMBER` no longer allocate per call.** Each of them built a `Vec` to hold something it needed for the length of one command: the old value while the new record was written, the text of a double, the indexes about to be removed, the permutation to draw from. The string cases go through the database's scratch buffer, the doubles go on the stack, `LREM` uses a `Small`, and `ZRANDMEMBER` gets an index buffer of its own.
- **A multi key set operation no longer allocates once per key.** `SINTER`, `SUNION` and `SDIFF` each built a handful of vectors sized by the number of keys, and that number is two or three almost every time, so a `SINTER` over three small sets was doing about eleven allocations to hold about a dozen `usize`. It does none now.
- **The database's scratch buffer starts at a kibibyte instead of empty**, so its first growth is not on a command path either.

### Performance

Development measurements on an Apple M4 in the release profile, not gate numbers on a qualified box.

- **A large integer set, bytes per member.** 512 members went from 4.00 to 2.08, a thousand from 24.60 to 2.19, a hundred thousand from 30.92 to 3.53, and a million from 29.19 to 4.08. The three larger sizes were `hashtable` before and are `intset` now. A membership test at a million is 14.7 ns for a hit and 13.0 ns for a miss.
- **`LINSERT` and the walks around it.** `linsert_middle` at a million elements went from 3.34 ms to 456 us over two changes, `find_far` at a million from 6.57 ms to 904 us, and `lpos_far` at a million from 5.53 ms to 1.02 ms. On a million element list the insert itself is 285 ns, so essentially all of that was the search.
- **Filling a packed blob is a bit over twice as fast at every size.** `listpack_fill/8` went from 216 ns to 96, `/512` from 11.5 us to 4.62, and `list/push_back/1000` from 18.5 us to 11.5. The chunked band is untouched, because a chunk has always written into its own fixed array.
- **Small set operations.** `inter/ints/k2` went from 69.50 ns to 44.23 and `inter/ints/k3` from 88.34 to 58.28. The text cases barely move, because those plans build a hash table sized by the members and that is what they spend their time on.

### Known gaps

`YO_ALLOC=abort` is not armed in CI yet, and cannot be until the thirteen sites the report still finds are dealt with. They are written up on #146. Three of them are the old value being copied out on `SET ... GET`, `GETDEL` and `COPY`, which is a signature question rather than a two line fix, since the value goes back out to the caller as an owned `Vec`. Four are the data structures growing because somebody put more into them, which needs a decision about whether the first touch claim covers them. The rest are small and specific and are each worth fixing.

## 0.3.5 — 2026-08-31

Twenty three pull requests, no milestone, so this is a patch. It is a much bigger one than the two to five changes RELEASING.md describes, and the reason is worth writing down rather than glossing over: the thing that makes a release mean anything only landed in the middle of it. Nothing this project has ever tagged was published anywhere, so `cargo add yodb` at any version from 0.1.0 onwards resolved a name and no version. This is the first release that actually goes to crates.io, and eighteen crates go up with it.

Two whole types arrived in this window, the sorted set and the array, which is 35 of 35 sorted set commands and 17 of 18 array commands. The list picked up its five blocking commands and is now 22 of 22. Set against that, cutting a patch after every three pull requests would have produced seven sets of release notes for one story told in pieces.

The `.yo` layout is untouched. Two in memory layouts moved, the collection element table and the list chunk index, and neither of them is written to a file, so a file written by 0.3.4 opens unchanged.

### Added

- **The sorted set, all thirty five commands.** `ZADD` through `BZMPOP`, in six pull requests: the counted B+ tree that holds rank, the type over it, the twenty two single key commands in the keyspace, the algebra and the multi key commands, and then four rounds of putting them on the wire. Every table field, every reply and every error sentence was read off a running Redis 8.10.1 rather than written from the documentation, which is how the reply shape differences got found. `ZRANK WITHSCORE` on a member that is not there is the array nil and without it the string nil, and a RESP2 client tells those apart. `ZPOPMIN key` is a flat member and score where `ZPOPMIN key 2` is a list of pairs. A missing key answers an empty array to a sorted set pop and a null to a list pop. None of that is in a manual.
- **The counted B+ tree.** It holds row numbers and nothing else, so a search asks the caller where the thing being looked for sits against a given row and the caller reads that row's score out of the element table. Caching the score in the tree would finish the search without leaving the node and would cost eleven bytes an element rather than three. It measures 3.23 bytes an element at a hundred thousand members and a test asserts it.
- **The array type and seventeen of its eighteen commands.** Redis 8.8 added a type nothing else here looks like: a sparse vector indexed by an unsigned sixty four bit integer, running from zero to 2^64 - 2 with holes anywhere in between, where -1 is an error rather than the last element and `ARLEN` and `ARCOUNT` are different numbers. The store is a sorted vector of 4096 index slices that a read binary searches, which covers the whole index space in one structure where Redis needs a flat directory and a superdirectory above it. A value of seven bytes or less lives in the position word itself, and so does an integer that fits sixty one bits and a double whose canonical text is byte for byte what the client sent, so `007` stays a string and a client reads back what it wrote. Four new divergences are registered for it, D-18, D-19, D-20 and D-21.
- **The five blocking list commands.** `BLPOP`, `BRPOP`, `BLMOVE`, `BRPOPLPUSH` and `BLMPOP`, and then `BZPOPMIN`, `BZPOPMAX` and `BZMPOP` reused the same machinery for two new `Want` variants and one emptiness check. A parked client is a kept command rather than a suspended stack, so answering it later is running the same attempt again.
- **Publishing to crates.io when a tag goes out.** The whole workspace goes up, because crates.io has no way to publish a crate without publishing what it depends on. `xtask` is `publish = false` and stays out. crates.io goes first and the GitHub release goes second, since the notes tell people to add a dependency and a release that says so before the crate is there is a broken instruction for however long the gap lasts. The job asks crates.io which crates are already up at this version and excludes them, because eighteen uploads are not a transaction and a run that dies on the ninth has to be fixable by re-running rather than by burning another version number.
- **A measurement for what a list element costs.** M4's exit gate asks for one byte or less and nothing had ever put a number against it. It is 2.12 bytes at eight byte elements, 2.23 at sixteen and 3.92 at sixty four, and almost all of it is listpack framing rather than anything the chunk ring does. See the known gaps below, because this row is a fail and it is a fail for a reason that was decided on purpose.

### Changed

- **Every double on the wire is printed the way Redis prints one.** Redis writes doubles through `d2string`, which calls `fpconv_dtoa`, a Grisu2 it vendors under `deps/fpconv`. We were using Rust's `Display` on the grounds that both are shortest round trip printers and would therefore agree, and they do not, for two separate reasons. fpconv switches to an exponent for a large or small magnitude and Rust never does, so a score of ten to the thirtieth read back from us as a one and thirty zeros and from Redis as `1e+30`. And Grisu2 is not always shortest: it finds the shortest form for about nineteen values in twenty and emits one extra digit for the rest, so reshaping Rust's output would have left a few percent of all doubles still wrong. This is a port of fpconv kept line for line with the C, checked over two hundred thousand random bit patterns. `INCRBYFLOAT` and `HINCRBYFLOAT` turned out to be a different printer again, `ld2string` in its human mode, which is fixed point and has no exponent to switch to, so they get their own path.
- **A collection's arrays grow by a quarter once they are large.** Both the row array and the name blob were `Vec`s, and a `Vec` doubles, so a collection whose size sits just past a power of two held room for nearly twice what it was storing. Past sixty four kilobytes of allocation they grow by a quarter and under it they keep doubling, because under the threshold the slack is a handful of kilobytes however wrong the policy is and the copies are what matter.
- **A collection's payload lives beside its row rather than inside it.** A row is a six byte name reference and a four byte home slot, and a score is eight bytes and wants eight byte alignment, so a row carrying one was twenty four bytes to hold twenty. The payloads are in an array of their own now at the same index, the row is twelve bytes whatever the collection stores, and there is no padding anywhere. The size of a row is a test rather than a comment, because putting a score back inside it would compile and would quietly cost four bytes a member again.
- **A scan cursor is read in one place.** There are four scans on the wire and each had written out its own cursor parse and its own reply shape. Two of the four parses disagreed with Redis in different directions, one refusing a leading plus and a leading blank and the other taking a trailing blank as the end of the number rather than as a mistake. Redis parses a cursor with `strtoull` and then insists the whole argument was consumed and that there was no minus, and that is one function now with the cases in a test.

### Fixed

- **`COPY` of a list or a sorted set no longer takes the shard down.** `COPY` read the source value out through one match on the type tag, and that match had a catch all arm at the bottom from when a set and a hash were the only bodies there were. The list and the sorted set landed in it and reached `unreachable!`, so an ordinary command any client can send panicked a live server. `Body` has a variant for each type now and the remaining matches name the stream rather than catching it, which is the actual fix: a catch all in front of an enum the rest of the crate keeps growing reports itself as a panic in production instead of as a build error.
- **`cargo fmt`, which CI had been failing on since 0.3.4.** Five files were hand written in a more compact shape than rustfmt produces and never run through it, so every push for three commits was going red in the first minute. No logic touched.
- **Two of the four scan cursor parses, described above.** A leading plus, leading blanks and leading zeroes are all fine to Redis and a trailing anything is not, and we had one scan refusing the first group and another accepting the second.

### Performance

All of these are development measurements on an Apple M4 in the release profile, not gate numbers on a qualified box.

- **`LRANGE` over a window in the middle of a long list, 1.98 ms to 3.36 us at a million elements.** That is 589 times, and the number it was returning was never the hundred elements it hands back, it was the five hundred thousand it walked past to reach them, because `range` was `iter().skip(start).take(count)` and a skip on the element walk decodes every listpack header it passes. The same window costs 234 us to 2.38 us at a hundred thousand and 2.19 us to 0.77 us at a thousand.
- **`LINDEX` in the middle of a long list, 1078 ns to 290.8 ns at a million.** The ring carries where each chunk starts and a lookup is a binary search over that rather than a walk. The entries are in their own coordinate system whose origin is wherever the head chunk happened to be, which is what makes work at the front free: pushing on to the head moves that chunk's start back by one and leaves every other entry correct. Reads near an end pay three percent for a comparison they did not used to make and hold flat as the list grows.
- **The maintenance turn after every batch, four percent of the pump loop down to one point eight.** It walked all sixteen databases and asked each whether it had garbage to collect, and asking takes a load and a store inside a database that is a cold line on any server whose clients are all on database zero, which is every server. There is a bit per database now, set when a command runs against it and cleared when it says it has nothing.
- **A six hundred thousand member sorted set, 48.1 MB down to 33.9 MB.** Twenty nine percent, and it is the growth policy change. Ten thousand members went from 51.4 bytes of overhead an element to 25.8. A million barely moved because a million sits right on a power of two and doubling had no slack there, which was luck rather than policy.
- **A million member sorted set with sixteen byte members, 26.02 bytes per element in the row arrays down to 22.20.** That is the payload moving out of the row. What it could have cost is a walk that reads the member and the score, since those are two sequential streams now rather than one, and that case had no benchmark so it has one: 0.65 ns an element at a thousand, 0.79 at a hundred thousand, 0.98 at a million, which is the memory system and not the second array.

### Known gaps

- **`ARGREP` is the one array command missing.** It needs a regular expression engine, which Redis gets from `deps/tre`, so it is a dependency decision before it is a piece of work.
- **Two M4 exit gate rows now have numbers and both of them fail.** Three bytes or less per sorted set entry: the tree is 3.23 and the whole element costs 27.17 bytes of overhead, so the tree was never the problem and the element table is. One byte or less per list element: 2.12 at eight byte elements, and an entry in a Redis listpack is an encoding byte, its payload and a back length, so two bytes is the floor for anything holding elements in Redis's own bytes. That is the gate row describing the native band, which does not exist yet, and the inline band is byte compatible with a listpack on purpose because `05` section 4.1 asks for an RDB export to be a copy rather than a transcode. Every other M4 gate row still has no number.
- **There is no rival baseline in this release.** server1, server2, server3 and gpc have neither Redis nor Valkey installed at the moment, so nothing has been run against them, and the `GET` and `SET` deficit numbers being chased are from a local profile rather than from a gate run.
- **Trusted publishing is not on yet.** crates.io will take a GitHub Actions OIDC identity instead of a stored token, which would remove the only long lived credential in this repository, but it is configured per crate and a crate has to exist first. So this release goes out on the token and the next one should not.
- **M2 and M3 are still open on their exit gates,** which along with M4 is why this is a patch and not a minor. That has been true for five patches now.

## 0.3.2 — 2026-08-31

Sixty one pull requests and no milestone, so this is a patch, and it is a much bigger one than the rule in RELEASING.md intends. The cadence slipped while M2 and M3 were both moving at once and the honest fix is to cut what is there rather than to keep waiting for a milestone to close. M2 now has a server a Redis client can talk to and M3 has sets and hashes complete, but neither has passed its exit gate, so the minor that carries them is still to come.

The `.yo` layout is untouched. The record header in the arena gained a type tag in three bits that were already spare, and the numbers in it are the ones `yo-format` already writes on disk, so a record written by 0.3.1 reads back as a string, which is what it is.

### Changed

- **The executable is `yodb`, not `yo`.** `yo` on PATH is Yeoman's and has been for over a decade, and it is Yeoman's on Homebrew core, Chocolatey and the AUR, so shipping a binary called `yo` means shipping a collision into every channel we would want to publish through. Only the executable moves. The crate is `yodb`, the library is `libyo`, the header is `yo.h`, the symbols are `yo_*` and the file extension is still `.yo`.
- **A walk collects the dead keys it goes past.** A side by side run against redis 8.10.1 came back with one real difference: after `SET dead v PX 50` and a wait, Redis says `DBSIZE 1` and we said 2, because Redis has an active expiry cycle and we do not have one yet. A walk is the moment a dead key is found for free, so `SCAN`, `KEYS` and `RANDOMKEY` delete it now. They cannot delete during the walk, which holds a shared borrow of the index while it hands out borrowed keys, so the dead names go in a list and the deletes happen after, and the list stays empty on a database with nothing expiring in it.
- **`hash-max-listpack-entries` defaults to 512 and not 128.** 128 is the number everyone remembers and a running 8.10.1 with no config file says 512, so a hash of two hundred fields answered `hashtable` here and `listpack` there, and it would have carried on doing that quietly until someone read `OBJECT ENCODING`.
- **`yo_kv::Strings` is `yo_kv::Keyspace`.** It has owned the map and been the whole keyspace since M2, and only the name said otherwise. The twenty six string commands stay in `strings.rs` as an impl block on it, and the commands stay methods on the database rather than becoming methods on a per type object, because a key belongs to the database and not to a type: `DEL` does not care what it is deleting and `SADD` against a string has to be able to see that it is a string. `yo::Strings`, the handle the embedded API hands back, keeps its name, because that one really is only about strings.
- **`Ask::NoField` and `Applied::NoField` are `Ask::Missing` and `Applied::Missing`.** The enums were written for hash fields and they answer for keys too, and `NoField` reading back a key was going to confuse somebody.
- **The compaction threshold is an eighth dead rather than a quarter.** In the steady state a store holds about live divided by one minus this ratio, so a quarter was holding a third more than it was keeping and an eighth holds a seventh more. Measured over 100000 keys of 64 bytes rewritten four to thirteen times, that is 2 MB. Lower buys nothing, because below an eighth no segment qualifies until one of them is a quarter dead.
- **Maintenance runs once per batch rather than once per turn of the loop.** A turn carries one command or a thousand depending on how many clients are pipelining, so the rate at which garbage was collected had nothing to do with the rate at which it was made, and on a saturated server the second one wins. The same 400000 sets settled at seven segments on the server and six in a process running the writes directly, and the difference was entirely that the server never caught up.
- **A pull request is checked out at its head and not at `refs/pull/N/merge`.** The merge ref stops existing the moment the pull request is merged, and merging as soon as the local checks are green means the jobs that were still running lose the ref out from under them.

- **Comparing two short byte strings no longer calls `memcmp`.** `a == b` on two slices is a call into the platform's `memcmp`, which is the right answer for a megabyte and the wrong one for a key. `yo_common::bytes_eq` compares in machine words and stays inline, with the last word overlapping the one before it so that nineteen bytes is three loads and no tail loop. It is used at the three places the hot path always goes through: the key comparison in the index, the member comparison in the element table, and the memo in the keyspace.
- **An integer reply is formatted into a copy of a length the compiler can see.** `push_u64` was building the digits from the back of a twenty byte buffer and copying `buf[i..]`, a length only known at run time, which is a call into `memmove` that costs more to enter than it does to move a digit. The digits now go in from the front and the whole buffer is copied and cut back, and `i64_len` counts digits with `ilog10` rather than a loop of divides.

### Added

- **`yo-kv`, where the data structures actually live.** One method per Redis command, taking and returning ordinary Rust values, with no protocol anywhere near it. The wire calls into this and the embedded API calls into this, so there is one `INCR` rather than two that drift apart (Y23). An embedded program calls `Strings::incr` and gets back an `i64` or a `yo_common::Error`, without serialising a command, crossing a socket or parsing a reply.
- **The string type, which is the first row of M2.** All 26 commands: `SET` with `NX`, `XX`, `GET`, `KEEPTTL`, `EX`, `PX`, `EXAT`, `PXAT` and Redis 8.4's `IFEQ`, `IFNE`, `IFDEQ` and `IFDNE`, then `GET`, `GETSET`, `GETDEL`, `GETEX`, `SETNX`, `SETEX`, `PSETEX`, `MSET`, `MSETNX`, `MGET`, `APPEND`, `STRLEN`, `SETRANGE`, `GETRANGE`, `SUBSTR`, `INCR`, `DECR`, `INCRBY`, `DECRBY`, `INCRBYFLOAT`, `LCS`, and Redis 8.4's `MSETEX`, `DELEX` and `DIGEST` and 8.8's `INCREX`.
- **`LCS`, ported rather than reimplemented.** The backtrack is Redis's, quirks included, so the ranges `LCS IDX` reports land on the same bytes in the same order, `MINMATCHLEN` filters the same runs, and `len` is still the length of the whole subsequence and not the sum of what survived the filter. The documented `ohmytext` and `mynewtext` example comes out byte for byte.
- **`INCREX`, which is a counter with a policy attached.** Redis 8.8 put four ideas in one command: add an integer or a float, refuse or clamp a result that leaves a range, and set, keep, clear or conditionally set the deadline, all in the round trip that used to be `INCR` followed by `EXPIRE`. The reply is the value and the amount applied, so a client can tell a refused increment from one that added nothing without comparing against a value it did not have, and a refused increment does not create the key. The windowed rate limiter is one setting of it, `EX window ENX`, which starts the window only when there was no deadline, so a burst inside one window expires together rather than each call pushing the deadline out.
- **`DELEX`, compare and delete.** The other half of `SET ... IFEQ`, and the read modify write nobody was doing correctly: a client that reads a value, decides it is stale and deletes it can be beaten to the key in between, and `WATCH` plus `MULTI` costs a round trip to avoid that. It carries the same four conditions `SET` does, `IFEQ`, `IFNE`, `IFDEQ` and `IFDNE`.
- **`DIGEST`, and an XXH3 that is bit for bit Redis's.** Redis 8.4 added `DIGEST` so the digest conditions are worth using: a client holding a megabyte value sends sixteen hex characters instead of the megabyte. That only works if our number is the same number, so the implementation uses the real XXH3 secret rather than a hash that is merely good, and it is checked against digests read out of a running Redis at every length the algorithm branches on, which is both sides of 16, 128, 240 and the 1024 byte block.
- **A one byte header in front of every string.** Encoding in two bits, a deadline flag in a third, and eight bytes of deadline only for the keys that have one, which most do not. The alternative is a side table for the TTL, and a side table is a second cache miss on a path whose whole budget is one miss.
- **`INCR` that does not touch the arena.** An int encoded value stores the eight bytes of the integer rather than its digits, so incrementing it is a probe, an add and an eight byte store back into the record the probe landed on. No allocation, no free, no second record and no rehash. There is a test that increments a key a thousand times and asserts the arena's live byte count did not move.
- **`RawMap::set_with` and `RawMap::value_mut`.** The first lets a caller write straight into the record instead of building the value in a scratch buffer and having it copied in again, which is one memcpy per `SET` rather than two. The second is what makes the `INCR` path above possible.
- **`OBJECT ENCODING` that matches Redis, including the parts that look like bugs.** `SET k 007` is `embstr` and gives back `007`, `SET k 42` is `int`, the `embstr` boundary is 44 bytes, `APPEND` onto an existing key leaves `raw` even when the result reads as a number, and `APPEND` onto a key that is not there does not, because Redis runs the new value through `tryObjectEncoding` on create.
- **`commands.toml`, the command audit as a file rather than a document.** Every command carries a storage plan, a bound or materialise verdict, the Redis it came from, its arity, and how far up the stack it reaches. `cargo xtask check` enforces the rule from `12` section 3 that a command with no storage plan does not ship, and it enforces the group budgets too, so a group that claims 25 commands and holds 24 fails the same job a stale generated header fails. A document that says the same thing goes stale and nobody notices.
- **`divergences.toml`, the register of every place yo is knowingly not Redis.** Ten rows today, each one saying what diverges, why, and whether it is the design or goes away at a named milestone. A command marked divergent has to name a row that exists, and the check fails if it does not, so a divergence cannot be added in one commit and forgotten in the next. A compatibility claim with unlisted exceptions is how every Redis compatible product loses its users' trust exactly once.
- **`MSETEX`, `DELEX` and `INCREX`, checked against a running Redis 8.8 rather than written from memory.** The register shipped them marked `wire = "unverified"` because writing an argument order down from memory would make it look verified simply because it is in the code. Asking a real server settled it, and all three were wrong in substance and not only in argument order. `MSETEX` takes a key count and its condition is over the whole set, so `NX` needs every key missing and a partial match writes nothing. `DELEX` has four conditions rather than one. `INCREX` is the counter above and not the rate limiter it looked like. The string group is 26 commands and not 25, because `DIGEST` was missing.
- **A clock that only moves when it is told to.** `04` section 5 says there is no global clock read on the data path, so the shard reads the clock once per turn of the loop and all 64 commands in that batch compare against the same number. A clock read is tens of nanoseconds against a budget of a hundred and fifty, and paying it per command means paying it 64 times for an answer that did not change. Every expiry test in the crate drives a fixed clock instead of sleeping.
- **`yo-reactor`, the shard loop.** `04` section 2 is nine lines of pseudocode and this is those nine lines with the bookkeeping filled in. Six stages in one order forever: submit, drain a batch, enter the epoch, walk the batch twice, leave and flush, then completions and a bounded maintenance slice. There is no executor under it, no future, no waker and no work stealing. The loop is the scheduler.
- **The two walk batch.** A batch is 64 commands, and it is walked once to hash every key and ask the cache for the bucket that hash selects, then once to run them. Valkey and Redis 8.4 both use a window of 16 because they hold a lock across it and other threads can invalidate a line inside it, and Y1 removes both of those reasons. On a ten million key map the second walk is worth 13 percent on aarch64 and 20 percent on x86-64, and on a hundred thousand key map it is worth nothing on either because there was never a miss to hide.
- **A break that does not throw work away.** A command whose key set is not known until something earlier in the batch has finished, which is a `MULTI` body, a `WAIT` or a blocking form, ends the batch where it stands. What was already drained behind it waits for the next turn rather than being executed cold or dropped.
- **Inline execution, which is the embedded path.** A caller who is already on the shard thread calls `execute` or `execute_all` and gets the same prefetch and the same dispatch the server path gets, so a command has one implementation rather than two that drift. Y23 asks for the same code and not the same idea.
- **A maintenance budget in instructions rather than in wall clock.** Reading a clock is a syscall or at best a serialising instruction, and a wall clock slice does a different amount of work on a busy machine than on an idle one, so the tail it produces cannot be reproduced. A unit budget is a subtraction, and a pass that overshoots does so by one item instead of by however long that item took.
- **A software prefetch hint in `yo-common`.** One instruction on x86-64 and one on aarch64, nothing at all anywhere else, and nothing under Miri. It reads no memory and has no effect a program can observe, which is why the tests for it can only check that.
- **`Index::prefetch` and `RawMap::{hash_of, prefetch, get_hashed}`.** The first walk hashes a key and warms its bucket, the second walk looks it up with the hash it already has. A key in a batch is hashed once rather than once per walk.
- **`yo-shape`, the shape tag.** A C ABI erases types and a file outlives every process that opens it, so a Python program has no way to find out that the collection it just opened as a map of strings was written as a map of integers by a Go program in March. The tag is what finds out: a canonical byte description of the element type, in a grammar no language owns, hashed to 128 bits. Same type, same tag, in every language and on every machine. Field order is part of it, because order is layout, and so are integer widths, because "int" is a different number of bytes in every language that will open the file.
- **A shape mismatch that tells you what moved.** Comparing two tags answers "the same or not", which is the worst message a database can give: the reader knows something changed and nothing about what. So the description is stored beside the tag and a mismatch renders both shapes, underlines the part that differs, names the difference in a sentence, and says whether it is additive or breaking. Adding a variant to an enum reads as `enum Status gained variant "Cancelled" at position 3` with `change=additive` in the error's detail, and swapping two fields reads as a reorder rather than as two renames.
- **BLAKE3 in `yo-common`, written rather than depended on.** The same call the other three hashes in that crate got: the tag is a number six bindings have to agree on forever, so the algorithm is part of the format and belongs next to `crc32c` and `xxh3`. The published crate would also pull a C toolchain into every build in the workspace for a hash that runs once when a collection is opened. All 35 of the BLAKE3 team's own test vectors pass, from the empty input to a hundred kilobytes, which is what pins the chunk chaining and the tree.
- **`yodb`, the embedded API, which is the crate a person actually types.** Two lines get you a database and there is no third line: `yo::open(yo::MEMORY)` then `db.map::<String, u64>("hits")`. No server to start, no connection string, no pool, no schema to declare somewhere else first. `Map<K, V>` has `get`, `with`, `set`, `del`, `contains`, `len` and `is_empty`, and a lookup takes a borrowed key the way `HashMap` does, so a `Map<String, u64>` is read with `map.get("home")` and not with a `String` built for the length of one call. The package on crates.io is `yodb` because `yo` is taken, and the library inside it is `yo`, so `cargo add yodb` is followed by `use yo::open`.
- **The type parameters are the schema, and they are checked.** Opening a name a second time with a different type is refused before a single byte is read as the wrong thing, with the message from `yo-shape` saying what moved and whether the change is additive or breaking. That is what a query language usually buys you with a runtime error in production, bought here with a compile error on a laptop and one check when the collection is opened.
- **Zero copy per call rather than per database.** `get` hands back an owned value because that is what most code wants, and `with` hands the bytes over where they lie, which allocates nothing. Both read the same collection and the caller picks per call (Y29). On an Apple M4 a `with` on a million key map is 11.9 ns against the raw map's 10.5, so the shape, the handle and the decode together cost about 1.4 ns, and a `get` of a `u64` is 11.8 ns because it decodes out of the arena rather than copying out and decoding after.
- **A database that returns errors where it could have panicked.** A closure passed to `with` that calls back into the same database gets a sentence telling it to read first and write after the closure returns, rather than a `RefCell` panic from inside a dependency. A record larger than a segment is `YO_ERR_FULL` naming the limit, rather than an assert further down.
- **The Redis keyspace, reached without the socket.** `db.strings()` is the string keyspace and every method on it calls the same `yo-kv` method a command off the wire calls, so `SET`, `GET`, `INCR`, `MSET`, `GETSET`, `GETDEL`, `SETNX`, `APPEND`, `STRLEN` and the rest are one implementation with two doors rather than an embedded copy that agrees with the server for now (Y23). Keys are byte strings the way Redis's are, so a `&str`, a `String`, a `&[u8]` and a `Vec<u8>` all work and none of them are converted on the way in.
- **Inline execution mode, which is where the point read budget is actually spent.** The calling thread is the shard, so a command is a function call with no queue, no message and no wakeup (`15` section 7). On an Apple M4 the embedded path costs almost exactly what the store costs on its own: `GET` through `with` is 27.0 ns against the store's 24.5, `SET` is 36.3 against 33.9, `INCR` is 10.1 against 10.8 and an eight pair `MSET` is 162 ns against 156, so the handle, the borrow and the `AsRef` together are worth two or three nanoseconds against a budget of a hundred and fifty. `get` costs 54.7 ns because it hands back an owned `Vec`, which is the copy `with` is there to avoid.
- **A clock that stays off the data path even with no loop to refresh it in.** `04` section 5 keeps the clock read out of the command path and the shard loop refreshes it once per turn, but inline mode has no loop, and reading the clock per call costs 10 ns on top of an 18 ns `GET`. So the clock is read only when its answer can be observed: a keyspace that has never been given a deadline cannot hold an expired key, and the first call that sets one turns the reads on for good. `Db::reads_the_clock` says which state a database is in, and there is a benchmark for both.
- **`db.counter("hits")`, the handle that holds the key.** Counting is the commonest thing a string key is used for and spelling the key at every call site is one more place for a typo, so `Counter` has `get`, `incr`, `decr`, `add`, `set` and `reset` and reads as zero until something writes it, the way Redis's does. It is the same key the keyspace and a Redis client see, and `set` writes the digits without allocating.
- **`yo_resp::engine`, the seam between the loop and the commands.** The reactor knows how to run a batch and nothing about commands, dispatch knows how to run a command and nothing about where the bytes came from, and until now there was nothing in between, which is why there was no server. `Wire` is that piece: connections, per connection read buffers, framing that hands the reactor a batch of commands, a pooled decoder per command in flight, and the reply buffer each connection accumulates into. It implements `yo_reactor::Engine`, so the same two walk batch that was measured on a synthetic engine now runs real `SET`, `GET` and `INCR` off real wire bytes.
- **One write per connection per batch.** Replies build up in the connection's `Out` and go out in `flush`, which calls the sink once per connection touched no matter how many replies are waiting. aki's `HGETALL` profile spent 69.7 percent of its time in write syscalls and this is the shape that stops that happening again. A sink that takes fewer bytes than it was offered leaves the rest in the buffer and is offered it again next flush, so a full socket is backpressure rather than a lost reply.
- **What a command costs end to end, without a socket.** On an Apple M4, through framing, dispatch, the store and the flush: `GET` is 69.8 ns on its own and 46.6 ns each at a pipeline of sixteen, `INCR` is 87.6 and 59.6, `SET` is 102 and 75.7. Sixteen connections with one command each cost 910 ns against 754 ns for one connection with sixteen, which is the price of sixteen writes instead of one and the reason the flush is shaped the way it is. Everything a real command pays for except the kernel is in those numbers, so what memtier adds on top is the network stack and nothing else.
- **A `Sink` rather than a socket.** Where the bytes go is a trait with two methods, so the engine is testable without a network and the ring stays out of the crate that parses the protocol. The io_uring reactor implements it later and nothing above it changes.
- **`yodb serve`, which is a Redis client away from being a server.** Non blocking sockets, an accept loop, one read per connection per turn and one write per connection per batch, with the engine above it unchanged. `redis-cli` connects, `HELLO 3` switches the protocol, `SET`, `GET`, `INCR`, `INFO` and `COMMAND` answer, a pipeline comes back in order in one write, and `QUIT` closes. It listens on 127.0.0.1 rather than on every interface, because Redis shipped the other way for years and the result was tens of thousands of open databases on the internet.
- **A server that runs on all four machines the gate is measured on.** `04` section 7 puts the network on io_uring and that is still where this ends up, but three of the four boxes are not Linux, so a Linux only server cannot produce the macOS and Windows rows M2 asks for. The loop here is the same shape with a worse multiplexer: a readiness scan instead of a ring, which the ring replaces later without anything above it changing. A rough loopback number with a Python client driving it is 3.1 million operations a second at a pipeline of 100, which says the socket path is not in the way, not what the gate number will be.

- **The keyspace commands that make a key a key and not a string.** `DEL`, `UNLINK`, `EXISTS`, `TYPE`, `DBSIZE`, `FLUSHALL` and `FLUSHDB` came first because Redis's own test suite cannot get through a single file without them, and the rest followed with the types. `EXISTS` counts a key named twice twice and `DEL` counts it once, which looks like an inconsistency and is exactly what a real server answers, because one is counting arguments that matched and the other is counting keys that went away. `FLUSHALL` and `FLUSHDB` throw the index and the arena away and build fresh ones rather than deleting a key at a time, which would leave an arena the size of the data that used to be in it.
- **`EXPIRE`, `PEXPIRE`, `EXPIREAT`, `PEXPIREAT`, `PERSIST`, `TTL`, `PTTL`, `EXPIRETIME` and `PEXPIRETIME`.** Hash field deadlines landed before plain key deadlines did, which left the odd gap where a client could put a deadline on a field of a hash and not on the hash. The four writers turn their number into one absolute millisecond before they reach the store, so one place applies the condition and four commands cannot drift apart. Everything about the semantics came from asking a running 8.10.1 rather than from the manual, including that `TTL` rounds to nearest while `HTTL` rounds up, that the condition keywords are a set rather than a keyword so `EXPIRE key 100 XX GT` is legal, and that the condition is checked before the past check, so `EXPIRE key 0 NX` on a key that already has a deadline answers 0 and the key survives.
- **`RENAME`, `RENAMENX`, `COPY`, `TOUCH` and `TIME`.** A string lives in its record and a set or a hash lives in a slab with the record holding a tag and a slot number, which is why moving a value is two different jobs. `RENAME` writes the source's record bytes under the destination and drops the source without freeing anything, so renaming a set of a million members writes thirteen bytes. `COPY` cannot do that, because two records pointing at one slot would be one set answering to two names, so it clones the body, which is Redis's cost too.
- **`SCAN`, `KEYS` and `RANDOMKEY`, on a cursor that names a place in the keyspace.** Redis needs reverse binary iteration because its table doubles by adding a bit at the top of the bucket index. Our directory adds a bit at the bottom, so a left aligned 48 bit hash prefix is the same number before a doubling and after one, and walking in increasing prefix order is enough on its own. Any `u64` is a valid cursor, which is what Redis does and the only behaviour that does not need the server to remember every cursor it has handed out. `RANDOMKEY` picks a position and reservoir samples inside the bucket it lands in, with sixty four tries before it falls back to a full walk, so a database that has had almost all of it deleted answers the key that is left rather than nil.
- **The element table that every collection type sits on.** A hash, a set and a sorted set ask the same two questions of the same structure, so there is one table with a payload the caller picks rather than three that drift apart. A dense row array, a blob holding the interned names, and an open addressed slot array in front with a tag byte that throws out a collision on the low bits before a name is compared at all. A removal moves the last row into the hole and closes the slot by shifting the run behind it back, because `SPOP` in a loop deletes every element a set ever had and a table that answers an empty set by walking a million tombstones is slower than the structure it replaced.
- **The inline band, which is a real Redis listpack in Redis's own bytes.** The bytes are checked against Redis and not against a reading of Redis: `listpack.c` out of the 8.10.1 tarball was compiled against a small allocator shim, fed every boundary vector, and the hex it produced is in the tests, so CI checks the format with no Redis anywhere. It found one real bug, a back length boundary written as `len < 16383` where Redis has `l <= 16383`, which would have written an entry a real server walks off the end of.
- **The packed integer set.** A set whose members all parse as integers is held as the integers themselves, sorted, in the narrowest width that covers the widest of them, which is two bytes an element with no overhead at all and the number the M3 memory gate asks for. The layout is Redis's, both header fields little endian whatever the host is, so an RDB export is a copy and not a transcode.
- **The set, over all three representations, at all seventeen commands.** `SADD`, `SREM`, `SMEMBERS`, `SISMEMBER`, `SMISMEMBER`, `SCARD`, `SPOP`, `SRANDMEMBER`, `SSCAN`, `SMOVE`, `SINTER`, `SINTERCARD`, `SUNION`, `SDIFF` and the three store forms. The promotion rules are read off `t_set.c` rather than worked out, which matters because two of them are not what anyone would write: an intset past 512 members becomes a hash table and not a listpack, and an intset holding 200 integers goes straight to a hash table when it receives one string, because the count is compared against the listpack ceiling of 128 and not the intset ceiling of 512.
- **The hash, in a listpack and in an element table, at all twenty eight commands.** `HSET` through `HSCAN`, then the nine command `HEXPIRE` family, then `HGETDEL`, `HGETEX` and `HSETEX`. Values in the table band go in a blob the hash owns, one stretch of bytes for the whole collection rather than an allocation per field, and the dead byte accounting that already existed once inside the element table moved out so both callers use it. The reading commands take a closure and hand it a `Text` rather than returning bytes, because a value in the listpack band may be stored as an integer and writing the digits into the reply buffer instead of into the hash is what keeps a hash of counters at the size it is.
- **Field TTL, indexed by the row rather than by a `ttl_idx`.** A key keeps its deadline in the header of its value and a field has no header, so a field deadline lives in a side array allocated the first time any field of that hash is given one. A hash that never uses this carries three words and no allocation. The spec asked for an index held in the row and that was corrected to the row position, which is already in a register when the probe finishes, against four bytes in every row of every hash and a second dependent load on every read.
- **The downward scan cursor.** `SSCAN`, `HSCAN` and `ZSCAN` promise that everything present for the whole scan comes back at least once. Walking down from the top is what buys that: an insert appends above the cursor and is not returned, and a removal moves the top row down into the hole and may repeat one, and neither is a miss. Walking up would take an unvisited member and drop it into a visited position, which is the one case the guarantee exists to rule out.
- **The slab that holds a value which is not bytes.** A set owns three allocations that grow and shrink as members come and go, so rewriting the record on every `SADD` to keep them inline would copy the whole set once per member added. The record holds four bytes saying where instead. There is no generation counter on a slot and that is deliberate: the only way to hold a stale number is for a record to outlive the remove that freed it, and a generation would turn that into a `None` at the cost of eight bytes per record for every key of every type forever.
- **A type tag in the meta byte, and a `WRONGTYPE` that can actually happen.** Three of the five spare bits in the record header say what the key holds, so `TYPE` and every type check answer out of the cache line the lookup already fetched rather than out of a side structure. The type check in `INCR` is inside the probe rather than in front of it, and that is measured: in front it cost one and a half nanoseconds on a command that runs in eighteen, and inside it is three bits of a byte the probe has already loaded and costs nothing.
- **`OBJECT`, and the five thresholds behind it as the one thing `CONFIG SET` can move.** `ENCODING` is the one worth having and `REFCOUNT`, `IDLETIME` and `FREQ` are there because clients call them without thinking, all three saying the only honest thing there is to say. Moving a threshold leaves every collection that already exists where it is and only decides what the next write builds, which is Redis's rule, and `CONFIG SET` takes all of its pairs or none of them so a bad second pair does not leave the first one applied.
- **Serving on a socket file as well as on a port.** `yodb serve --unixsocket /tmp/yo.sock`, with `--no-port` if that is the only door wanted. Every wire number this project publishes is bounded by the loopback round trip and a Unix socket is the cheapest way past it: no IP header, no TCP state machine, no checksum and no Nagle. A socket file outlives the process that made it, so the stale case is told from the live one by connecting to it, because removing it blind would let a second server steal a running one's socket.
- **`SCRIPT` and `FUNCTION`, as far as a server with no interpreter can answer them.** Redis's test suite says `FLUSHALL`, then `FUNCTION FLUSH`, then `SCRIPT FLUSH` before every `start_server` block and gives up on the whole file when any of them fails. What is implemented is the part of both that is exactly right on a server whose script cache and library set are empty. The subcommands that would need an interpreter are not there at all and report an unknown subcommand, because an OK that did nothing is worse than an error for a client that loads a script and then calls it.
- **Sets and keys on the embedded side.** `db.sets()` is the keyspace shape with the key as the first argument and `db.set("online")` holds the key for you, the same two doors the strings already had. Every read that hands back members comes in both forms, `members()` allocating a `Vec` per member and `for_each()` handing each one over where it lies, which matters because a set of integers is stored as integers and walking a million of them with `members` formats a million numbers. `Keys` is the handle for the commands that belong to no type, with `exists`, `count`, `kind`, `del`, `expire_in`, `expire_at`, `ttl`, `deadline` and `persist`, and `ttl` answers an enum with three variants rather than Redis's three answers packed into one integer, because a key that is gone and a key that is never going away are different things and code that confuses them deletes the wrong data.
- **Two sets from two different databases cannot be intersected with each other.** Without the check a handle from elsewhere contributes its key and not its contents, so the answer is computed against whatever this database happens to hold under that name. That is not an error and not an empty result, it is a plausible wrong one, and there is a test with a decoy in it that would pass if the check were removed and the answer were merely empty.
- **`INFO` says where the memory went.** `used_memory` is one number and one number cannot tell you whether a store is holding too much because its records are fat, because nothing has come back for the ones it overwrote, or because its clients are sitting on buffers. `used_memory_dataset` and `used_memory_overhead` are Redis's names for the same split, and `mem_arena` and `mem_index` are ours and named so nobody mistakes them for something Redis reports. There is a CPU section now as well, with four of Redis's six numbers, because the two that are missing need `RUSAGE_THREAD` and reporting process totals under a thread's name would be a wrong number rather than a missing one.

- **Engine bench rows for the hot key shape, `engine/sadd` and `engine/srandmember`.** Both fill `set:hot` with 100000 members before the measured runs start, which is past every representation boundary, so the row measures the shape a hot key has in a benchmark that has been running for ten seconds rather than the listpack it passed through on the way there. The member `SADD` adds is one that is already there, which is the steady state of the gate row, because memtier draws from a fixed range and a run long enough to measure spends most of itself adding members the set already holds.
- **`YO_SPIN_FILL` in the `spin` profiling target.** It puts N members in the command's key before the loop starts, so `spin` can be pointed at the same hot key shape the bench measures.

- **The list type, in the two representations Redis has and one it does not.** A list is one listpack while it is under eight kilobytes, which is what `list-max-listpack-size -2` means and why a list of a thousand short strings is still one blob, and it is a ring of chunks after that. `OBJECT ENCODING` answers `listpack` and `quicklist` the same as Redis does, and the boundary in both directions is Redis's own: a list converts back to a listpack only once it is under half the limit and only once it is down to a single node, which is the hysteresis that stops a list sitting on the boundary from rebuilding itself on every second command. The type and its operations are here and the commands are not: `LPUSH` and the rest of the family reach the wire in a later release.
- **A chunk is a run of entries with a cursor at each end, not a listpack.** A quicklist node is a listpack, and taking the first element out of a listpack moves every byte behind it left, so Redis pays a memmove on every `LPOP` of a long list. A chunk holds the same entries in the same encoding and keeps a head cursor and a tail cursor, so a pop at either end moves a cursor and touches nothing the other end owns. A push at the end that has no room left slides the live bytes over once and splits what is free between the two ends, which is what keeps a list that is pushed and popped at the same end from allocating a chunk per push.
- **The listpack element codec is shared rather than copied.** `entry_len`, `write_entry`, `decode` and the back length pair are internal to `yo-kv` now instead of private to the listpack, so the chunk encodes an element exactly the way the listpack does. That is what makes promoting a list out of the packed band a single copy of the listpack's entry region rather than a walk that re-encodes every element, and it is what keeps an integer stored as an integer across the band change.

### Fixed

- **Building an error message would have aborted the server.** An error carries a `String`, a shard thread that allocates aborts, and every error message in `yo-kv` is built on a shard thread, so the first client to send `INCR` at a key holding a word would have taken the process down with it. It has not happened yet only because the reactor is not wired to the string type, which is the next pull request. Constructing an error is now allowed to touch the heap, since an error is by definition off the path the hundred and fifty nanosecond budget is about, and `Error::fmt` exists for the messages that need formatting because `format!` allocates before the constructor ever sees it.
- **`INCREX` obeyed a range it should have refused.** `LBOUND 10 UBOUND 5` is a range nothing fits in, and refusing every increment forever is a hard bug to find in a caller that has its arguments the wrong way round. A real 8.8 answers `ERR LBOUND can't be greater than UBOUND` and now so does this.
- **`INCRBYFLOAT` stored `raw` where Redis stores `embstr`.** A float counter that lands on a short result gets `tryObjectEncoding` run over it on the way in, the same as `SET` does, so `SET k 5` followed by `INCRBYFLOAT k 1` leaves `embstr` and not `raw`. `APPEND` and `SETRANGE` really do leave `raw` even for four bytes, which is what made the wrong behaviour look right. The old test asserted the bug, so it was locked in until `INCREX BYFLOAT` was written from what a real server reports and the two disagreed.
- **`parse_i64` accepted `-0`, which Redis does not.** Redis's `string2ll` tests its zero case against the length of the whole string, so the minus sign pushes `-0` past it and into the one to nine gate, which it fails. That is not only a parsing detail, because the same rules decide whether a string is stored int encoded. Left alone, `SET k -0` would have been stored as the integer zero and `GET k` would have handed back `0` for a value the client wrote as `-0`.

- **A server held every version of every key it had ever been sent.** Overwriting a key wrote a new record and only counted the old one dead, and nothing ever compacted. On server3, 400000 sets over 100000 keys of 64 bytes came to 72.8 MB of `used_memory` and 85.8 MB of RSS, against Redis 8.10.1 at 14.1 and 21.9 and Valkey 9.1.1 at 11.7 and 18.7. Segments come back now: a compacted segment goes on a free list and is bumped through again, compaction walks the segment rather than the whole index so a pause scales with a segment and not with the size of the database, an emptied segment gives its pages back to the kernel with `MADV_DONTNEED` while keeping its mapping and its index, and an arena stops taking a segment until something is put in it, which is thirty megabytes a server was holding for the fifteen databases nobody uses.
- **A read buffer kept every byte the connection had ever sent.** The framing loop only ever stops on an incomplete command and a connection that is exactly caught up gives one of those every time, so a decoder was parked almost always and compaction refused to run while one was. Measured on server3 with 400000 sets of 64 bytes: four connections held 16 MiB apiece and fifty held 1 MiB apiece, which was 41.8 MB of the 63 MB of RSS either way. A half read command is not in the way, because its decoder keeps offsets from the front of the slice it was handed and cannot tell whether its bytes arrive at the front or at the read cursor.
- **A pooled decoder carried on from where the last command stopped.** A protocol error stops framing where it is and hands the decoder back, and so does a connection that hangs up with half a command in its buffer. From a client that looked like sending one malformed frame, getting the right error and the close, reconnecting, sending anything at all, and getting nonsense or nothing back. Redis's `unit/protocol` is a list of malformed frames each on its own connection, so it hit this on the second test and hung there.
- **A client that pipelined behind `QUIT` got answers it should not have.** Redis gives one reply and one closed connection when `QUIT` and `SET` come out of the same buffer, and we gave two, because framing happens before anything runs and both commands were already queued. The other half of it was found while testing the first: a protocol error was written into the reply buffer the moment framing hit it, which put it in front of replies the client was still owed for commands that were framed out of the same read and had not run yet.
- **`HSET h a 1 b 2` stored the key as the first field.** An off by one in the pair walk. The wire tests caught it on the first run.
- **`INCRBYFLOAT` refused hexadecimal floats that a real server accepts.** Redis parses every float with `strtold` and `strtold` takes hexadecimal, so `0x10` is sixteen and `0x1.8p1` is three on a real server and was an error here. Nobody designed that syntax into Redis and it is unlikely anyone leans on it, but it is the kind of difference that turns up in production rather than in a test. A string that starts `0x` and then stops being a number is refused rather than falling through to the decimal parser, which would have called `0xzz` a plain zero.
- **The unknown command sentence had an empty clause in it.** Redis says `unknown command 'NOTACOMMAND'` when there are no arguments and only adds the `with args beginning with` clause when there is something to put in it.
- **`INCREX` with `SATURATE` could report an amount applied that had wrapped.** The reply carries both the new value and how much of the increment really landed, and saturation can put the value far enough from where it started that the subtraction overflows.
- **Three checks that only went red away from a mac.** `Door` has a single variant on a platform with no unix sockets, so the `if let` that walked the listeners for a port was an irrefutable pattern there and clippy refused the build; `EVENTS` sizes the array the epoll and kqueue backends read into and is dead code on the fallback backend, so it is behind the same cfg as the two that want it. The third was a test rather than the library: a freed segment gives its pages back with `MADV_DONTNEED` on Linux, which promises that reading them again gives zeroes, so the header `reclaim` had just written was gone by the time the test read it, and macOS keeping the pages was the only reason the assertion ever passed. There is an `Arena::is_free` now, kept beside the mapping rather than in it, and the test asks that instead.
- **The name audit was reading our own placeholders as shipped software.** The placeholders were republished at 0.0.1 because some registries will not take the same version twice, and three probes told a real release from a placeholder by comparing against a literal 0.0.0, so nine rows started claiming a real version is published where there is a package that raises on every call. The same 0.0.0 was baked into the sentence every placeholder raises with in all seven languages, so a user who installed 0.0.1 and called something was told the version of a package that is no longer on the registry.

### Known divergences

Ten new ones, all listed here rather than left to be discovered. The register is `divergences.toml` at the root and it holds seventeen rows now, seven of which came out of the spec before any of this was written. A command that diverges has to name a row that exists or `cargo xtask check` fails, so a divergence cannot be added in one commit and forgotten in the next.

The first four are in the string type.

- A string is capped just under 2 MiB rather than at Redis's 512 MiB, because a value lives in one arena segment. The band above that is the log region in `06` section 2 and lands with tiering in M5, at which point the cap goes up to Redis's. A value past the cap is a `YO_ERR_FULL` carrying Redis's own message and not a panic.
- Expiry is lazy only. A key past its deadline is dropped when something touches it, and it is dropped at the exact millisecond, since a deadline equal to now has passed. The active cycle that would reclaim a key nobody ever touches again is maintenance slice work and lands in M5.
- `LCS` refuses a table over 64 million cells, which is 256 MiB of counters and two strings of about eight thousand bytes each. Redis has no explicit limit and fails on the allocation instead, which on a server that has overcommitted is a kill rather than an error, and `LCS` on two large strings is the easiest accidental denial of service in the string group.
- The float counters count in `f64` where Redis counts in the C `long double`, which is eighty bit on x86-64 and a hundred and twenty eight bit on aarch64. Redis therefore does not agree with itself across machines and we agree with ourselves everywhere. A value that needs more than seventeen significant digits differs and nothing else does.

The other six came with the server and the keyspace.

- `HELLO` and `INFO` report the server as redis 8.8.0, because every client library in the world branches on that pair to decide which commands exist, and a driver that reads `yo` there falls back to its oldest code path or refuses to connect. The honest answer is in the `yo_version` field of `INFO`, next to `redis_version`.
- `COMMAND INFO` sends empty tips, key specs and subcommands. The first, last and step triple is filled in and correct, which is what a cluster aware client routes on. The three fields after it describe request policies and key flags that nothing in this engine has yet, and an invented answer is worse than an empty one, because a client that finds the field trusts it. It goes away at M6.
- `CONFIG` reports nine settings and refuses a change to any of them but the five collection thresholds. Accepting a change nothing acts on would be worse than refusing it: a client that sets `maxmemory` and gets an OK has been told it has a limit. It goes away at M5.
- `DBSIZE` counts a key that is past its deadline until somebody reads it or a walk goes past it. Both servers answer from the size of the index rather than by walking it, and the difference is that Redis has an active expiry cycle taking a sample out every tick. Making `DBSIZE` walk instead would turn an O(1) command into an O(N) one for a number that is already approximate on a real server. It goes away at M4.
- `SCRIPT` and `FUNCTION` answer for an empty cache and refuse the rest, which is described above and goes away at M6.
- `PEXPIREAT` clamps a deadline past the year 4199, because a record holds the deadline in forty six bits. The command answers 1 either way and the key does not expire either way, so the only thing a client can see is `PTTL` naming a different absurd number than the absurd number it asked for. Refusing it would break a client that uses a large constant to mean never, and widening the record would cost eighteen bits on every key with a deadline to hold a range no clock will reach.

### Internal

- **`Engine::prefetch` takes the work as well as the hash.** A hash says which bucket to warm and not which structure it is in, and the database a command lands in comes from that connection's `SELECT` rather than from the key, so two commands in one batch can carry the same key into different databases and later into different types. Every implementation gains one parameter it is free to ignore.
- **`Server::db_ref`, a database without taking it mutably.** The prefetch stage runs for all 64 commands in a batch before any of them executes, so it cannot hold the mutable borrow `run` is about to want, and it does not need one: warming a cache line reads nothing and changes nothing.
- **`MSET`, `MSETNX` and `MSETEX` take an iterator of pairs rather than a slice.** The wire layer has its pairs as positions in the connection's read buffer, so a slice would mean collecting them into a `Vec` before the call. `MSET` is one of the four commands M2 is measured on and a shard thread that allocates aborts, so an API that forces an allocation to call it is the wrong API. The iterator is walked twice, which is why it has to be `Clone`, and an iterator over borrowed slices is two words to copy.
- **`parse_f64` moved from `yo-kv` to `yo-common`, next to `parse_i64`.** Same reason the integer one moved out of `yo-resp`: whether an argument is a float and whether a stored value is a float are the same question, and the answer should not live in a layer the other one cannot reach.
- **`num.rs` moved from `yo-resp` to `yo-common`.** Whether a bulk length parses and whether a string is stored int encoded are the same `string2ll` question, and the answer should not live in the wire layer where the storage layer cannot reach it without depending on the protocol. `yo_resp::num` still resolves and still means what it meant.

#### Not making the garbage, rather than collecting it faster

The first gate run put yo between 0.32x and 1.19x of the faster rival with the write rows at the bottom, and the cost tracked how much garbage a command made rather than how much work it did. `set_with` allocated a fresh record and freed the old one on every overwrite even when the new value was exactly the size of the one already there, which is the shape every `SET` benchmark has and the shape half the world's caches have. A record of exactly the right size is written where it lies now. Same machine, redis-benchmark, 48 connections over 4 threads, 64 byte values over a million keys:

| row | before | after | p99 | peak RSS |
| --- | --- | --- | --- | --- |
| SET P16 | 998,004 | 1,331,558 | 3.94 ms to 0.91 ms | 84.8 to 74.2 MB |
| SET P1 | 173,822 | 190,404 | 0.65 ms to 0.66 ms | 83.7 to 74.0 MB |
| MSET P16 | 132,978 | 299,401 | 14.6 ms to 5.2 ms | 130.1 to 113.0 MB |
| MSET P1 | 92,250 | 133,274 | 4.02 ms to 0.69 ms | 127.5 to 112.2 MB |

Faster and smaller at the same time, which is unusual enough to say out loud: the record that is not written is also the record that does not have to be held until something collects it.

Giving a segment back over many calls instead of one is the other half. Compaction used to evacuate a whole segment inside one step, which is two megabytes and around twenty six thousand records with the whole batch of replies queued behind it, and that is what the write tail looked like. On the same machine with `--data-size-range=32-1024` and `--data-size-pattern=R`, which is the load that actually makes garbage now, throughput went from 696,702 to 767,921 with the p99 from 2.99 ms to 2.27 and the p99.9 from 3.98 to 3.11, for no extra memory. The slice size is not fixed: the floor is what a command can be asked to wait for and the number of segments waiting says how much more than the floor it takes to keep up, because one segment waiting means the collector is keeping up and nine waiting means it is not.

#### One probe where there were two or three

`GET` used to look a key up three times, once to see whether the deadline had passed, once to check the type and once to read it, each of which is its own cache miss on a database that does not fit in cache. In process on a hundred thousand keys it goes from 77 ns to 35 ns, best run against best run, and the ratio is worth more than either number because the box was not quiet. Every set and hash command started with a reap and then a get for the same reason, and folding those took a hot key `SADD` from 47.0 ns to 29.1 ns on an M1, which is the single member onto one key shape that has no spread to exploit. `SPOP` was allocating a `Vec` per member on the way out and copying all of it into the reply buffer, and it now writes each member straight from the set into the buffer, which the tests check with a counting allocator rather than by assertion: the borrowing draw allocates zero times for a whole set in each of the three representations.

#### Two calls that were not doing any work

A profile of `SADD` against a set that already holds the member spent seven percent of the command inside the platform's `memcmp` and eleven percent inside its `memmove`. The `memcmp` is `a == b` on two byte slices, which the index probe, the element table probe and the keyspace memo each do to check that the key they landed on is the key they were asked for, and for nineteen bytes the call and the length dispatch inside it are most of the cost. The `memmove` is the integer reply, where a `:0` went out of line to move one byte because the length of the copy was only known at run time.

Both are gone from the profile. The minimum of seven interleaved runs on a laptop that was not quiet, before against after: `SADD` on a hot key 71.5 to 70.0 ns, `SRANDMEMBER` 74.6 to 72.0, `SET` 69.6 to 69.5, `INCR` 59.8 to 56.7, `GET` on a missing key 37.7 to 37.2. `INCR` moves most because it pays for both, and `SET` barely moves because its reply is a constant and its key is compared once. These are development numbers on a machine that has other work on it, not gate numbers.

#### What the structures cost

Membership against a member that is there, minimum per iteration, on an M3 laptop, which is the measurement that decides where the bands sit:

| members | intset | listpack | element table |
| --- | --- | --- | --- |
| 8 | 4.6 ns | 6.2 ns | 7.7 ns |
| 64 | 6.6 ns | 29.5 ns | 10.2 ns |

The listpack band is not there because it is fast, it loses every timed operation at every size in the band. It is there because it costs 13.1 bytes an element against the table's 31.0 with an eleven byte member, and because `OBJECT ENCODING` has to answer `listpack` for exactly the collections a real server answers it for. The spec argued for that band on speed and has been corrected to say what was measured. The intset is 2.0 bytes a member for five hundred and twelve small integers against the listpack's 3.0 and the table's 24.0, which is the number the M3 memory gate asks for.

The element table itself, at a thousand, a hundred thousand and a million elements: probe hit 9.9, 16.2 and 16.2 ns, probe miss 9.4, 9.3 and 9.3 ns, draw 4.4, 4.5 and 4.8 ns, walk 0.76, 0.88 and 0.88 ns per element, overwrite 15.2, 22.0 and 19.6 ns, fill 19.7, 41.1 and 52.8 ns per element, pop 6.5, 25.7 and 79.8 ns. The draw is the row that was pre-registered at 4.8 ns at a hundred thousand and 12.2 ns at a million, and it comes in at 4.5 and 4.8.

One prediction did not survive contact. K11 registered a crossover between probing the smallest set and counting everything into one table at k around seven, and it does not exist: probing wins at every k from 2 to 16 and the two lines converge without crossing, because a counting touch hashes its member and makes its own random access in exactly the same way a probe does, and both measure about 25 ns. The crossover comes back when the partitioned band gives sorted arrays walked in lockstep, whose touch is a pointer step with no hash, and that is M4.

#### Memory

Peak RSS on server3 for 400000 sets over 100000 keys of 64 bytes: 15184 kB, against Redis 8.10.1 at 21976 and Valkey 9.1.1 at 18856. That is the memory column of the M2 gate, which scores our peak against the leaner of the two, and it is the first time it has passed. The last four megabytes of it came from not keeping a free segment warm, which was saving one `madvise` and one huge page fault per two megabytes written and costing more than the whole margin the gate was missing by.

### Known gaps

- There is no active expiry cycle. A key past its deadline is dropped when something touches it and now also when a walk goes past it, which is what makes `DBSIZE` after a `SCAN` answer what Redis answers. A key nobody touches and no walk reaches is still counted until something does, and the maintenance slice that will collect it is written into `14` and not implemented.
- The M2 and M3 exit gates are both open. The pipelined `SET`, `SADD` and `SPOP` rows sit at 74, 68 and 66 percent of the measured PING ceiling against a gate of 85, and the 200 thousand durable commits a second row still wants NVMe with SQPoll on the box `bench/00` section 7 describes, which none of the four machines is.
- The keyspace group is missing `DUMP`, `RESTORE`, `MIGRATE`, `MOVE`, `SORT`, `SORT_RO`, `WAIT` and `WAITAOF`. The first four want the export and import pair `COPY ... DB` already built, and the last two want replication.
- Lists and sorted sets do not exist yet. The element table, the listpack, the scan cursor and the slab are all shared, so both types are commands over structures that are already here rather than new structures.
- The C ABI describes strings and typed maps and does not describe sets or keys, so an embedded caller in C cannot reach either yet. `api.model.json` is the file that has to gain them, and the header and the bindings are generated from it.
- There is no Lua and there will not be until M6, so `SCRIPT` and `FUNCTION` answer only what an empty script cache and an empty library set can honestly answer.

## 0.3.1 — 2026-08-28

Four pull requests and no milestone. `yo-resp` and `yo-uring` are M2 pieces, the fuzz and crash work and the ring wiring are M1 evidence, and none of the four closes the milestone it belongs to, so this is a patch. The on-disk format is untouched.

### Added

- **`yo-resp`, the RESP2 and RESP3 codec.** The first piece of M2. Requests decode into ranges over the connection's own read buffer, so a command sees the bytes the kernel delivered and nothing is copied on the way in. Replies are written straight out as wire bytes with no intermediate value, which is Y18. Multibulk and inline requests, every RESP2 and RESP3 type, Redis's own limits, and Redis's own protocol error text character for character.
- **One reply path for both protocols.** A command writes a map, a set or a push and the RESP2 downgrade happens in the codec rather than in the command. That is one place to test instead of three hundred, and it is what stops a command from working on one protocol and not the other.
- **A resume state on the request decoder.** A value that arrives in ten thousand pieces is scanned once rather than ten thousand times. Without it a slow link makes the parser quadratic in the size of the value, which is a real denial of service on a real network rather than a theoretical one.
- **A protocol fuzz target.** `12` section 11 point 3. It checks that no input panics or allocates from a count off the wire, that a decode reports exactly what it consumed, and that feeding the same bytes one at a time reaches the same verdict as feeding them all at once.
- **A file fuzz target, which is the M1 exit gate the project did not have.** The gate is that the independent reader agrees with the engine on every file the fuzzer produces, and until now there was no fuzzer producing files. It builds a real `.yo` file from fuzzer chosen record shapes across up to four shards, walks it with the engine's own replay and with the independent reader, and compares both against what went in, then compares the superblock and the checkpoint entries field for field between the two sides.
- **The hundred thousand fault crash gate, as a nightly job.** Every push runs twenty thousand faults, which catches a regression and fits the three minute budget. The gate number is a hundred thousand and now runs in `deep` across five shapes, so the number in the milestone is a number CI produces rather than one somebody ran once.
- **`yo-uring`, the per shard submission ring.** The second piece of M2 and the thing the last open M1 exit gate row is waiting on, because that row asks for SQPoll and SQPoll is io_uring. One ring per shard, four thousand and ninety six entries, storage and network submissions on the same ring told apart by the user data tag, which is `04` section 7 exactly.
- **Parked state instead of an async runtime.** A submission that has not finished has its caller's state in a slot, and the next turn of the loop picks it up when the completion arrives. There is no future here, no waker, no executor and no `.await`, which is what `16` section 0 means when it disqualifies anything with an executor in it. The VLDB 2026 io_uring ladder is 16.5 thousand transactions a second when every submission is waited on and 183 thousand when the execution is restructured this way, so the parking is the design rather than an optimisation.
- **A tag that makes a stale completion detectable.** Eight bits of kind, twenty four of slot, thirty two of generation. The kind routes storage against network with no lookup. The generation is the correctness part: a slot is reused the moment it is freed, so without it the completion for a cancelled read lands on an unrelated connection and nobody ever finds out why.
- **The same state machine on macOS and Windows, not a gate and not a stub.** `04` section 7 asks for synchronous storage off Linux with the shape kept, so that is what is there. `Features::is_uring` says which of the two produced a row, because a benchmark number that does not say which kernel path it took is a number that will eventually be wrong.
- **The log writes through the ring.** `LogFile::use_ring` puts a shard's log on the submission ring, and from there the shard hands bytes over and keeps going rather than stopping for a `pwrite` and an `fdatasync`. This is the piece the 200 thousand durable commits a second row in M1 has been waiting on: `yo-uring` existed, nothing used it, and a ring nothing writes through is not a measurement.
- **A staging buffer pool, because a borrow cannot be handed to the kernel.** `PageWrite<'_>` gives its borrow up when the call returns and the kernel reads the buffer long after that, so the bytes are copied into a buffer the writer owns and the buffer goes back on the free list when the completion arrives. The pool stops growing once it is as deep as the writes in flight, and the copy is a memcpy against a syscall.
- **At most one write in flight per page.** io_uring does not order two submissions against each other, and every flush of a page rewrites that page's header, so two in flight at once could land with the older header last and leave a page claiming fewer records than it has. A second write to a page waits for the first. In group mode this never waits, because the sync boundary has already drained everything.
- **A sync that waits for the writes it covers.** A queued `fsync` runs in parallel with the writes queued ahead of it, so `sync` records the address it has to cover and returns, and the `fsync` goes out from `poll` once the last write has landed. That is the most common way to get an io_uring durability bug and it is why `durable_upto` moves in exactly one place.
- **`PageSink::poll` and `Log::poll`.** Where an asynchronous sink runs its state machine, once a turn of the shard loop, and therefore where a caller parked on `CommitAction::WaitFor` stops being parked. A synchronous sink takes the default and does nothing.
- **A `commit_ring` benchmark row.** The synchronous path against the ring, in group mode, at batches of 64, 512 and 4096, waiting for durability on both sides so the two columns are the same measurement. It prints whether the ring was really io_uring, because off Linux it is the portable backend and that number is not a gate row.

### Changed

- **`sync` durability mode parks the caller when the sink is asynchronous.** It used to sync and reply, which is right when the sync has finished by the time the call returns and is a reply before the fsync when it has not. It now replies immediately if the sink is already there and otherwise waits on the address, exactly like group mode. Same guarantee, reached later, and no change at all for a synchronous sink.
- **`os` durability mode submits at a page boundary.** That mode promises the operating system has the bytes, and with a ring under it the bytes sit in the submission queue until something submits them. A page boundary is once per 32 MiB, so the call costs nothing anybody can measure.

### Fixed

- **Two hundred megabytes of build artifacts were committed to the repository.** The fuzz directory is excluded from the workspace and has a build directory of its own, and `.gitignore` said `/target`, which is anchored to the root and did not cover it. 895 object files were tracked. They are untracked now and the pattern covers any depth. The history has been rewritten to drop them as well, so a fresh clone is 824 KB rather than 53 MB. Every file in every commit is byte for byte what it was, only the commit hashes moved, and the four release tags were rewritten and force pushed along with `main`. A commit hash written down before 2026-08-28 will not resolve, which is the price of the rewrite and is worth it once.
- **Two ring tests passed everywhere except on the platform they were about.** They polled once after a sync and asserted durability had moved, which is true of the portable backend, where the write and the fsync both happen inside the call that submits them, and false of io_uring, where the first poll picks the write completion up and only then lets the fsync go out. They now turn the loop until the address moves, with a cap so a real stall is a panic rather than a hang. Cross compiling had said the Linux path was fine and running it said otherwise, which is the whole argument for running on the machines rather than checking against them.

### Performance

Both tables are development measurements and neither is a gate number. Group commit, both columns waiting for durability so they are the same measurement, `commit_ring` at three batch sizes, throughput in commits a second.

macOS aarch64 on APFS, the portable backend rather than io_uring: 17.1 thousand against 17.8 with the ring at a batch of 64, 131.3 against 129.6 at 512, and 866.6 against 835.1 at 4096. The ring column pays for a memcpy and some bookkeeping and gets no asynchrony back, because off Linux there is none to get, so being a few percent behind is the expected result and not a regression.

Linux x86_64 on server3, kernel 6.8, ext4 on a virtio disk, real io_uring: 4.9 thousand against 3.9 at 64, 47.9 against 22.9 at 512, and 132.4 against 142.0 at 4096. The 512 row was re-run on its own with more samples and came back the other way at 37.0 against 42.1, so that gap was the box. Error bars on this machine are around plus or minus 30 percent, which is what a shared VPS on a QEMU disk gives, and at that spread the two columns cannot be told apart in either direction.

### Known gaps

- The 200 thousand durable commits a second row in M1 is still open, and as of this release the reason is hardware rather than missing code. The path runs end to end on real io_uring and lands the same bytes as the synchronous path, but the row asks for NVMe with SQPoll on the box described in `bench/00` section 7, and none of the machines available is that box.
- Registered buffers are unimplemented and `Features::registered_buffers` reports false. The staging pool is what they will attach to.
- `IORING_OP_URING_CMD` is deliberately out of scope for v1, per `04` section 7.

**Milestone: DX0, the ABI contract.** No engine work. This is the surface every binding will sit on, described once and generated from that description, so that the header, the error codes and the machine readable model cannot drift apart. RELEASING.md gives a minor to every engine or DX milestone, and this is the first DX one.

## 0.2.0 — 2026-08-28

**Milestone: M1, the record plane and the file.** M0 was a workspace and the pieces every milestone stands on. This is the first release that writes anything down. A `.yo` file, a hybrid log over it, replay, compaction, an independent reader that shares no code with the engine, a checker built on that reader, and a crash injection harness with an exact oracle.

### Added

- **`yo-format`.** The byte layouts and nothing that touches a file: superblock, checkpoint entry, page header, record framing, and the encode and decode for each. Both the engine and the independent reader are written against the same document rather than against each other, which is the only arrangement where a disagreement means something.
- **`yo-record`.** The hybrid log. Mutable, read only and stable regions over a ring of resident pages, per shard epochs, group commit with four durability modes, replay, and F2 style lookup based compaction with dead byte accounting deciding when it runs. `Log<S>` is not `Send`, so installing a record is a store rather than a compare and swap.
- **`yo-file`.** The `.yo` file. Two superblocks at 0 and 16384 with the root flip done as sync the data, write the slot that is not live, sync again. Log addresses count payload bytes rather than file bytes, so every page address is an exact multiple of the payload length and asking whether a segment is where it says it is is arithmetic rather than a guess.
- **`yo-reader`.** A second reader that shares no code with the engine. It is not a test double. It is the only thing that can catch the format drifting away from what is written down, and it is what makes a yanked release still readable.
- **`yo check`.** The tool you run when a database will not start. It separates a usage failure from a verdict, so a file that is not ours exits 2 and a file that is ours and damaged exits 1, and it never writes to the file it is checking.
- **`yo-crash`.** Crash injection with an exact oracle: lose everything, lose a prefix, reorder, tear at sector granularity, scatter, and flip a bit, against an image that only holds what a sync covered. Every damaged image is read twice, by recovery and by the independent reader, and compared record by record and on where the walk stops. Seeded with splitmix64, so a failure is a seed somebody can type in.
- **A `crash` CI job**, running a fifth of the gate across four shapes on fixed seeds. Fixed rather than drawn from the clock, because a job that picks its own seeds fails once a month on a seed nobody wrote down.

### Changed

- **The deep workflow went from 88 minutes to 6, and no check was dropped to get there.** The slowest job is now `miri (tree, yo-record-rest)` at 5 minutes 42 seconds, and the run finishes 20 seconds behind it. Miri was the whole of it. `cargo miri test --workspace` walks the crates one after another, so the wait was every crate added together; it is now one job per crate, taken from `cargo metadata` rather than from a list in the workflow, so a crate added next month gets interpreted without anybody remembering. Inside a job it runs through nextest instead of the built in harness, which matters because `cargo miri test` is a single process and libtest's threads do not help: Miri interprets threads on one core. nextest gives each test its own process, so a four core runner interprets four tests at once. `yo-record` locally went from 322.7 seconds to 121.2 at 359 percent CPU, and four interpreters on the heaviest crate peaked at 865 MB between them, so the parallelism costs megabytes and buys minutes. `yo-record` is split again by hand into its compaction tests and everything else, because those are half the crate and there is a floor to how far they shrink. The five fuzz targets run at the same time rather than one after another, which is five minutes down to one, and they share nothing so there was never a reason for the queue.
- **`format!` is gone from the test loops that run under Miri.** Miri charges per operation rather than per instruction, so the formatting machinery costs a couple of milliseconds a call where the same bytes built by hand cost microseconds. `yo-index` calls it once per set, get, delete and contains, which is ten thousand calls in one test, and taking it out took that crate's shard from 102.8 seconds to 57.7 locally. `yo-common` went from 16.7 to 9.1 the same way. The keys and values are byte for byte what `format!` produced, so no test is checking anything different.
- **Slice equality instead of a byte at a time loop in the arena tests.** Both read all six megabytes, but `==` on `[u8]` bottoms out in `memcmp`, which Miri runs as a shim rather than interpreting, and one test went from 265 seconds to 0.062. Nothing is skipped to get that.
- **Two dead ends, written down so nobody pays for them twice.** `--release` does not help Miri: `yo-record` measured 309.8 seconds against 309.7 for debug, because the cost is interpreted MIR operations and optimisation does not remove them. Neither does a slicing by eight CRC, which is the same eight table lookups per eight bytes however it is written. Both are real on hardware and neither is a Miri lever.
- **The `deep` job timeouts came down from 45 minutes to 25 for Miri and 15 for the rest.** A timeout well above the expected time is a job that hangs for three quarters of an hour before telling you.

### Known trade

nextest does not run doctests, so the `yo-crash` doctest is no longer interpreted under Miri. It still runs in `ci.yml` on every push, so what was lost is the doctest being interpreted, not the doctest.

### Fixed

- **A `yo-format` test never finished under Miri.** Flipping every bit of a 16 KiB superblock slot and decoding after each one is sixteen thousand iterations, each copying and checksumming 16 KiB. Natively that is a few milliseconds. Interpreted it did not finish inside a CI job's six hour ceiling, and it took a nightly Miri run with it. Under Miri the walk is now a stride of 2039 bytes plus nine offsets visited by hand, which is about 22 seconds; every ordinary run still flips every byte.
- **The log handed the store the previous tenant of a page, and it was a silent corruption.** Writes go out a block at a time, so a flush part way through a page sends the end of log sentinel and then the rest of the block behind it, and those trailing bytes were whatever the previous tenant of the ring slot left there. The same block goes out again on the next flush with more records in it and nothing syncs in between, so a device may take one sector from the first write and the neighbouring sector from the second. The page then comes back with a used mark from the later write and a sentinel sector from the earlier one, and the earlier one has a stale record where the sentinel should be. It parses, because a record's checksum covers its own bytes and says nothing about the address they belong at, and replay walked into it and handed back a record that was never written there. The tail of the block past the sentinel is now zeroed on the way out, which costs under a block per flush. Found by `yo-crash` at seed 26281, 400 records into an 8192 byte page, after a hundred thousand trials at the default shape had run clean.
- **`Reader::records` capped its walk at the page header's `used` field.** A crash can take the header write and leave the record writes, and on that file the reader reported fewer records than the file holds while recovery found all of them. `used` now sizes the first read and nothing else, and the walk runs to the sentinel, which is what replay does.
- **The commit benchmark was measuring a tmpfs** and was wrong by four orders of magnitude. It now takes its directory from `YO_BENCH_DIR` and prints the device's `fdatasync` floor next to the result, so the two can be read together. Any commit rate published before this should be discarded.

### Format

The `.yo` layout is defined by this release and is not frozen. `MAGIC` is `tamndyo fmt001`, superblocks are 16 KiB at 0 and 16384, the data area starts at 32768, and a region is 32 MiB. A minor release may still change any of it before `M6`.

Not changed but worth writing down, because it is the shape of the bug above: a record cannot be tied to its address. Any future path that puts old bytes under a new address ends the same silent way. Mixing the address into the record checksum would close that off and it is a format change rather than a fix, so it is not in this release.

### Performance

Development measurements. Not one of the machines available meets the gate box definition in `bench/00` section 7, so nothing here is a gate number.

- Durable commits, group mode, on gamingpc, an i9-13900K under WSL2, release profile with fat LTO and one codegen unit: the `commit_batch` curve crosses 200 thousand per second at a batch of roughly 1024, on a device whose `fdatasync` costs 2.3 milliseconds. Development measurement, and the batch size and the device floor are part of the number rather than footnotes to it.

### Known gaps

- **The two performance rows of the M1 gate are open**, and the reason is the box rather than the code: 200 thousand or more durable commits per second in group mode on NVMe with SQPoll, and a 10 GB file opening in under 100 ms. Neither gamingpc nor server1, server2 or server3 qualifies under `bench/00` section 7. No row from those machines is a gate row.
- `yo-file` still bump allocates regions and never reuses a freed one.

## 0.1.1 — 2026-08-28

A CI release. Nothing in the library changed, and a `0.1.0` file, API and ABI are all still exactly what they were. What changed is how long you wait to find out whether a change is good.

### Changed

- **CI is split into a fast path and a deep path, and the fast path is held to three minutes.** `ci.yml` runs on every push and every pull request: style, the debug test matrix on Linux, macOS and Windows, the MSRV floor, loom on the lane, and the docs build. `deep.yml` runs nightly, on demand against any ref, and on a pull request carrying the `deep` label: Miri under both borrow models, the fuzzers, the release test matrix, the benchmark smoke run, and the cold build from source. The reason is that a check slower than a context switch is a check people learn to route around, and the slow half was reaching six hours while the fast half was done in ninety seconds. Nothing was deleted. A milestone pull request carries the `deep` label and waits for all of it, which is now written into RELEASING.md.
- **Debug info is off in CI and the cache is only written from main.** `CARGO_PROFILE_DEV_DEBUG=0` cuts what rustc emits and what the linker then has to chew through, which is worth about a third of the Windows wall clock and most of the cache size everywhere, and no CI job here reads a backtrace line number. `save-if` on the cache means a pull request reads main's cache and skips the upload, which was twenty to forty seconds a job spent saving something the next pull request would not have used.
- **The debug and release test matrices are separate.** The test job used to build the whole workspace twice. The release half moved to `deep.yml`. A bug that only shows up under optimisation is real, it is just not worth paying for on every commit.
- **The two Miri borrow models run as two jobs rather than one job doing both in sequence.** They have nothing to say to each other, so the wait is the slower of the two rather than their sum. The check name changes from `miri` to `miri (stacked borrows)` and `miri (tree borrows)`, and `fail-fast` is off so one model failing still leaves the other model's answer on the same run.
- **Every job has a timeout.** A Miri job was killed by the runner's own six hour ceiling after sitting on a single test, which is a long time to wait to be told nothing. Miri gets 120 minutes and everything else less.

### Known gaps

- Miri and the fuzzers no longer gate an ordinary pull request. A patch that introduces undefined behaviour can now land and be caught the following morning by the nightly rather than before the merge. That is the trade the three minute budget is bought with, and the `deep` label is the way to pay it back on a change that deserves it.

## 0.1.0 — 2026-08-26

**Milestone: M0, Skeleton.** The parts every later milestone stands on, built first and on their own so that a mistake in them is found now rather than underneath a hundred thousand lines. Nothing here is a database yet. It is a workspace, a hash, an allocator, a bucket, a shard runtime and the CI that keeps them honest.

### Added

- **Workspace.** Rust edition 2024, resolver 3, stable 1.98.0, MSRV 1.94. The MSRV is held about six months behind stable and is a CI job, not a note in a file.
- **`yo-common`.** Hashing, log addresses, Redis slot arithmetic, and the error type. Errors are generated at build time from `errors.toml`, so a code, its message and its documentation cannot drift apart: there is one place to change and three outputs.
- **`yo-alloc`.** A global allocator that aborts. Not a fallback and not a measurement helper: a test that runs the hot path under it either does not allocate or does not finish. The claim that the statement path is allocation free is worth nothing unless something enforces it.
- **`yo-arena`.** Bump allocation in 2 MiB segments, with `MADV_HUGEPAGE` on Linux. One pointer add per allocation and a whole segment released at once.
- **`yo-index`.** The 64 byte bucket, which is one cache line, holding a word of tags matched with SWAR so a probe touches one line and compares eight tags in a few instructions. Growth is a dashtable split, so it is per bucket rather than a stop the world rehash of everything.
- **`yo-shard`.** One thread per core, one owner per thing. `ShardLocal<T>` is neither `Send` nor `Sync` by construction, which is the property that removes the locks rather than a comment asking people not to share.
- **Fuzz targets** for the bucket, the arena, the map and the lane.
- **CI, nine jobs**, and the ones that matter are the slow ones: Miri over every unsafe block under both stacked and tree borrows, loom on the lane, cargo-fuzz, a three OS test matrix in debug and release, the MSRV floor, a docs build with warnings denied, a benchmark smoke run, and a build from a source tarball with no git history.

### Performance

Development measurements, all of them. Not one of the machines available meets the gate box definition in `bench/00` section 7, so nothing here is a gate number and none of it should be quoted as one. Taken on gamingpc, an i9-13900K inside a WSL2 VM, pinned to core 0 with `taskset`, release profile with fat LTO and one codegen unit.

- Bucket tag match: **0.80 ns** on a hit, **0.53 ns** on a miss. The M0 gate is 4 ns or under, so this clears it with room, on a box that does not qualify.
- Arena bump allocation: **1.23 to 1.27 ns**, against **28.2 to 30.9 ns** for the system allocator on the same shapes. The gate is 2 ns or under.
- Hashing, wyhash against fnv1a, by input length: 3.08 against 2.32 ns at 8 bytes, 4.18 against 25.6 ns at 64 bytes, 12.1 against 153 ns at 256 bytes. fnv1a wins at 8 bytes and loses by an order of magnitude everywhere else, which is why wyhash is the default.
- Map get, hit, at a thousand keys: **12.3 ns**. This one is in cache and is **not** comparable to aki's 46.5 ns at a million keys. The comparable row needs a quiet machine with a working set that does not fit in L2, and it is not being reported until there is one.

### Fixed

- The shard benchmark was measuring `format!` rather than the map. Any shard number published before this should be discarded.
- Undefined behaviour in `Bucket::tag_word`, found by Miri, fixed by taking the pointer from the bucket rather than from the tag array.
- Two build failures that were invisible on the arm dev machine and only showed up on x86: an `unused_unsafe` warning around the crc32 intrinsics, and the `chunks_exact` to `as_chunks` migration. Every commit is now built on x86 before it lands.
- Windows CI was failing on line endings. Fixed with `.gitattributes` and a normalizer in the tooling rather than by turning the check off.
- A `yo-shard` test counted jobs across four lanes through a fifth one and expected an exact total. Ordering is per lane and a shard polls its lanes in turn, so jobs sent on one lane can still be queued when a call on another lane comes back, and the count was short. It passed on a quiet machine for weeks and failed once on a loaded macOS runner. The test now waits on each lane it used. Nothing in the runtime changed: no job was ever lost, `send` spins until the lane takes it.

### Known gaps

- **There is no qualified benchmark box.** server1, server2 and server3 are all below the kernel 6.12 io_uring floor and all oversubscribed. gamingpc clears the kernel floor but is a hybrid P and E core CPU inside a WSL2 VM sharing the machine with other work. Every number in this release says which it is. Rival comparisons start at `M2` and need a box that qualifies first.
- Nothing is stored. There is no file, no log, no records and no protocol. Those are `M1` and after.
